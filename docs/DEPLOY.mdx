# Deploy, Docker e Segurança Operacional

Guia de implantação do BackBet: Docker Compose, reverse proxy/TLS, política de **segredos**, listas de verificação pré-deploy e operação no servidor.

## Docker Compose

| Compose | Finalidade |
|---------|-----------|
| `docker-compose.yml` | Host único: MongoDB (replica set `rs0`) + Redis + `backbet` + workers |
| `docker-compose.test.yml` | Infra de teste isolada (Mongo replica set + Redis + `integration-tests` na rede Docker) |
| `docker-compose.proxy.yml` | Reverse proxy (Caddy/TLS) opcional |
| `docker-compose.observability.yml` | Prometheus + Grafana + OpenTelemetry Collector (opcional, liga o `/metrics`) |

Produção (mesmo host):

```bash
docker compose up -d --build
```

Mongo e Redis ficam **sem porta pública** (serviços internos do Compose); só a API e o proxy de TLS são expostos.

> Após mudanças de dependências/schema: `npm run docker:rebuild` (rebuild limpo da imagem).

## Proxy e TLS

- `docker-compose.proxy.yml` sobe **Caddy** com certificado automático; `deploy/proxy/Caddyfile` define o domínio público.
- Produção sugerida: `https://api.backbet.com` (HTTPS + cert automático, HSTS opcional).
- Verificação pós-deploy: `curl -sf https://$PUBLIC_DOMAIN/health` e `curl -sfI ... | grep -i strict-transport-security`.

## Segredos — política e gestão

Regra máxima: **nenhum segredo no Git.** `.env` é ignorado; `.env.example` só contém exemplos seguros.

### Catálogo

| Variável | Descrição | Obrigatório? |
|---|---|---|
| `JWT_SECRET` | Assina tokens JWT | **Sim, sempre** (`env.ts` lança sem ele) |
| `MONGODB_URI` | Conexão Mongo (embute usuário/senha) | **Sim em produção** |
| `REDIS_URL` | Conexão Redis | **Sim em produção** |
| `MONGO_ROOT_PASSWORD` | Admin do Mongo | Sim (compose) |
| `MONGODB_APP_PASSWORD` | Usuário `readWrite` da app | Sim (compose) |
| `MAILER_SMTP_URL` | URL SMTP do worker de contato | Não (sem valor → `jsonTransport`) |
| `SMTP_PASSWORD` / `SMTP_USERNAME` | SMTP do health-monitor | Só com `OBS_ENABLE_EMAIL_ALERTS=true` |
| `GF_ADMIN_PASSWORD` | Admin do Grafana | Só com observability |
| `PM2_WEB_PASSWORD` | Auth da WebUI do PM2 | Não (default inseguro `change-me-now` — **troque**) |
| `OTEL_EXPORTER_OTLP_HEADERS` | Collector OTLP | Só com tracing remoto |
| `PAYMENT_PROVIDER_KEY` / `PIX_PROVIDER_KEY` | PSP (futuro) | Só com PSP real |

### Como o código protege

`src/shared/config/env.ts`: lança erro sem `JWT_SECRET`; em produção exige `MONGODB_URI`/`REDIS_URL`; nunca loga valores (boot expõe só `hasJwtSecret: boolean`); credenciais em URL exigem percent-encoding.

### Guard de CI: `npm run check:secrets`

`scripts/check-secrets.cjs` varre apenas arquivos rastreados pelo Git (`git ls-files`) e falha se encontrar nomes sensíveis (`.env*`, `.pem`, `.key`, `credentials`), chaves AWS/Stripe/GitHub, JWTs, e URLs `smtp(s)://user:pass@` / `mongodb://user:pass@` com credencial real. Já roda no `npm run check`.

### Secret managers (produção)

O MVP usa `.env` + `env_file` do Compose (atende a fase 26). Para operação real:

- **Doppler / 1Password CLI**: `doppler run -- docker compose ...` sem `.env` em disco;
- **Hashicorp Vault / AWS Secrets Manager**: lidos no entrypoint (`scripts/entry.cjs`).

A troca não altera código — `env.ts` continua lendo `process.env`.

### Rotação

- Rotacione `JWT_SECRET`, `MONGODB_URI`, SMTP e chaves de PSP de forma planejada; reinicie API + workers após rotacionar (config lida no boot).
- Credenciais de banco rotacionadas exigem atualizar também o backup/restore (`docs/BACKUP_RECOVERY.mdx`).

## Segurança Operacional (checklist pré-deploy)

| Item | Situação | Onde/passo |
|---|---|---|
| HTTPS | Configurado | Caddy + cert automático (`deploy/proxy/Caddyfile`) |
| Firewall | Configurado | `deploy/harden-server.sh` (UFW: 22/80/443, deny default) |
| SSH por chave | Configurado | Mesmo script — recusa desabilitar senha sem chave instalada |
| SSH root desabilitado | Configurado | `PermitRootLogin no` no script |
| Updates automáticos | Configurado | `unattended-upgrades` no script |
| Mongo/Redis privados | Configurado | Serviços internos do Compose + UFW default deny |
| Logs sem segredos | Configurado | `env.ts` loga só `hasJwtSecret`; guard `check:secrets` |
| Backups testados | Configurado | `npm run backup:*` + `/docs/BACKUP_RECOVERY.mdx` |
| Monitoramento/alertas | Configurado | `deploy/observability` + alertas (12 regras) |
| Scan de dependências | Gate no CI | `npm run audit:prod:critical` falha o build se houver crítica |

### Scan de dependências

|---|---|---|
| `npm run audit` | Todas | Relatório completo |

## Endurecimento do servidor

No host Ubuntu, **antes** de subir a aplicação:

```bash
sudo bash deploy/harden-server.sh
```

Idempotente e seguro; recomendações: usuário admin com `sudo`, nunca `root` direto; `ufw status verbose` e `ssh -i <chave> usuario@<ip>` testados em nova sessão antes de fechar a atual; `fail2ban` opcional.

## Verificação operacional (pós-deploy)

```bash
npm run check:secrets                    # sem segredos no Git
npm run audit:prod:critical              # 0 críticas em produção
curl -sf https://$PUBLIC_DOMAIN/health   # HTTPS + Caddy ok
ufw status verbose                       # só 22, 80, 443
npm run backup:drill                     # ciclo de recuperação ok
```
