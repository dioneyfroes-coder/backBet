# Ambientes de Teste (Fase 18)

A **Fase 18** organiza o projeto em três ambientes conceituais e garante que a
suíte de **integração real** (MongoDB + Redis) seja **reproduzível** — ou seja,
não depende de um MongoDB/Redis pessoal, de dados locais, nem de configuração
específica da máquina de desenvolvimento.

| Ambiente | Infraestrutura | Como rodar |
|---|---|---|
| **development** | Local do PC dev (Mongo + Redis via `docker run` ou Compose), app com `npm run dev` | Ver `docs/QUICKSTART.mdx` |
| **test** | **Docker Compose versionado** (`docker-compose.test.yml`): MongoDB `mongo:7` como replica set `rs0` de nó único + Redis `redis:7` | `npm run test:integration:full` |
| **production** | Host único em Docker via Compose: MongoDB (replica set `rs0`) + Redis + API + workers | Ver `docs/DOCKER.mdx` (Fase 17) |

## Por que uma infra de teste em Compose?

- Transações MongoDB (wallet/ledger/bet/treasury) exigem **replica set**; o
  compose de teste sobe o `rs0` automaticamente (`rs.initiate()` idempotente).
- Os testes de idempotência/atomicidade usam Redis de verdade.
- Nada disso precisa existir na máquina do dev — `npm install` + Docker bastam.

## Pré-requisitos

- Docker Engine + **Docker Compose v2** (recomendado **v2.20+** por conta do suporte a `up -d --wait`).
- Node.js 22+ (`engines` do `package.json`).
- **Nenhuma** instância local rodando nas portas `127.0.0.1:27017` (Mongo) ou `127.0.0.1:6379` (Redis) enquanto a infra de teste estiver de pé.

## Comandos

```bash
# 1. Sobe Mongo (replica set rs0) + Redis na máquina (portas só em 127.0.0.1)
npm run test:infra:up

# 2. Roda a suíte de integração real
npm run test:integration

# 3. Derruba a infra (os volumes são mantidos para a próxima execução)
npm run test:infra:down
```

**Tudo em um comando** (levanta a infra, roda os testes e derruba a infra,
mesmo que os testes falhem):

```bash
npm run test:integration:full
```

Para **começar do zero** (apaga dados do Mongo/Redis de teste e religa tudo):

```bash
npm run test:infra:reset
```

## Configuração de conexão do runner

O orquestrador `scripts/run-integration-tests.cjs`:

- define `RUN_REAL_INTEGRATION_TESTS=true`;
- roda o Jest com `--runInBand` no spec `src/integration/__tests__/mongo-redis.integration.test.ts`;
- lê **`MONGODB_URI`** / **`REDIS_URL`** do ambiente (shell ou `.env`; o dotenv
  nunca sobrescreve variáveis já exportadas) e **não tem fallback** para
  localhost/IP fixo — se faltar alguma variável, o runner aborta com erro claro;
- o `env.ts` também **não fornece mais defaults localhost** em modo teste: as
  URIs são obrigatórias sempre que Mongo/Redis forem usados (a suíte unitária
  hermética roda sem elas, pois usa adaptadores in-memory);
- usa o database de teste **`MONGODB_TEST_DB`** (default `backbet-test`): deriva
  da `MONGODB_URI` trocando só o database, ou usa **`MONGODB_TEST_URI`**
  literalmente (credenciais do usuário dedicado `backbet-test`). Assim a suíte
  **nunca acessa o banco da aplicação**.

Para rodar contra a infra local de teste do compose (loopback, sem auth):

```bash
npm run test:infra:up
npm run test:integration    # com .env apontando para a infra de teste
```

Para direcionar a suíte a **outra** infra (ex.: um ambiente de teste remoto),
exporte as variáveis antes de rodar:

```bash
export MONGODB_URI="mongodb://backbet-test:senha@host:27017/backbet-test?authSource=admin&replicaSet=rs0"
export REDIS_URL="redis://:senha@host:6379"
npm run test:integration
```

## Como a infra de teste foi montada

- **`mongodb`** — `mongo:7`, `--replSet rs0 --bind_ip_all`, healthcheck com `mongosh`.
- **`mongo-rs-init`** — container one-shot que inicia o `rs0` e só termina quando
  o nó única vira `PRIMARY` (espera até 30s). O membro anuncia `127.0.0.1:27017`
  porque o **Jest roda no host** e precisa descobrir o primary pela porta publicada.
- **`redis`** — `redis:7-alpine`, healthcheck com `redis-cli ping`.
- Portas publicadas **somente em loopback** e Mongo **sem autenticação**: essa
  infra é efêmera/local e não deve ser exposta na rede. Para produção, use o
  `docker-compose.yml` (Mongo autenticado + Redis + API + workers no mesmo host).

## Rodando a suíte dentro do compose de produção (host único)

O compose principal (`docker-compose.yml`) tem o serviço **`integration-tests`**
(profile `tests`) que usa a imagem `backbet:test` — estágio `tests` do
Dockerfile com **devDependencies + fonte TS** (a imagem de produção
`backbet:latest` é podada com `npm prune --omit=dev` e não contém Jest). Ele
conecta nos endpoints **internos** `mongodb:27017` e `redis:6379` e só executa
depois de o Redis estar saudável e o `mongo-rs-init` ter concluído (readiness
antes dos testes):

```bash
# no host (com Docker)
docker compose --profile tests run --rm integration-tests
# ou via script do package.json
npm run test:integration:docker
```

Requisitos no `.env` do host: `MONGODB_URI`, `MONGODB_TEST_URI`,
`REDIS_URL`, `JWT_SECRET` (o serviço falha na interpolação se faltarem). A
`MONGODB_TEST_URI` usa o usuário dedicado `backbet-test` (criado no boot do
Mongo pelo `deploy/mongo/init-app-user.sh`), com acesso somente ao banco
`backbet-test`.

## Pipeline completo (Fase 19) — gate obrigatório + endpoints reais

Antes de considerar uma entrega terminada, rode o **pipeline completo**:

```bash
npm ci          # instalação reproduzível a partir do package-lock.json
npm run check   # GATE OBRIGATÓRIO = lint + test:coverage + build (tudo verde)
```

Nenhum merge para `main` se qualquer um dos três falhar (lint ❌, testes/coverage ❌,
build ❌). O CI (`.github/workflows/ci.yml`) aplica o mesmos passos.

**Teste de endpoints REAIS** (sem Docker/Mongo/Redis, persistência in-memory):
sobe o binário compilado (`dist/index.js`) e exercita via HTTP o fluxo completo:

```bash
npm run smoke
```

O smoke valida: `/health`, `/health/cache`, `/api/docs.json` (Swagger), catálogo
de eventos, `register` → `login` → `me` → `deposit` → `withdraw` (validação de
mínimo) → **aposta real** → `bets/me` (estaca abatida do saldo) → **cancel**.
(refund do saldo) → `refresh`. Ao final imprime `SMOKE: N/N checagens OK`.

> Dica (Fase 19): os eventos de exemplo do repositório in-memory agora usam IDs
> **UUID** (ex.: `3fa85f64-5717-4562-b3fc-2c963f66afa6`), porque o `PlaceBetDTO`
> exige `z.string().uuid()` — antes os eventos demo não podiam ser apostados
> pela API real.

**Docker (deploy real)** — `docker compose build` / `docker compose up` exigem
Docker Engine; no PC de dev não há Docker, então esses passos rodam no host
Docker (ver `docs/DOCKER.mdx`) seguindo:

```bash
# no host (com Docker):
docker compose build         # imagem backbet:latest
docker compose up -d         # MongoDB + Redis + API + workers
```

## CI (GitHub Actions)

O workflow `.github/workflows/ci.yml` tem um job `integration` dedicado que sobe
a **mesma** infra (`docker compose -f docker-compose.test.yml up -d --wait`),
roda `npm run test:integration` e derruba a infra (`down`) sempre — provando que
o ambiente de teste é reproduzível fora da máquina do dev.

## Cenários críticos (Fase 20) — matriz de dinheiro

A **matriz de cenários críticos** (Carteira/Aposta/Settlement/Withdrawal/Pix)
vive em [`MATRIX-CENARIOS-CRITICOS.mdx`](./MATRIX-CENARIOS-CRITICOS.mdx) e
aponta, cenário a cenário, o arquivo:linha que o valida.

Testes adicionados na Fase 20 (rodam no `npm run check` normal, sem infra):

| Teste | O que garante |
|---|---|
| `src/core/betting/domain/services/__tests__/BetService.critical.test.ts` | saldo insuficiente; **rollback de transação** (falha pós-débito restaura saldo, não persiste aposta/ledger); **aposta simultânea** sem dupla cobrança (`balance >= 0`, débitos do ledger casam) |
| `src/infrastructure/api/__tests__/Settlement.integration.test.ts` | **settlement via HTTP** — WON credita retorno, LOST não credita, replay com `Idempotency-Key` não paga duas vezes, `result` inválido → 400, não-admin → 403 |
| `src/infrastructure/withdrawals/__tests__/WithdrawalPayoutWorker.safety.test.ts` | **worker**: entrega duplicada (sequencial e concorrente) paga 1x; timeout do provedor não debita e retry conclui; resposta duplicada do provedor não debita 2x (guarda do ledger) |
| `src/infrastructure/api/__tests__/RiskLimit.integration.test.ts` | **Fase 20.1** — limita a exposição via `RISK_CONFIG` e prova via HTTP: aposta que estoura o teto → `400 RISK_REJECTED` sem debitar a carteira (e aposta menor continua passando); blacklist → `RISK_REJECTED` sem débito; fecha a lacuna B7 da matriz |

**Risco registrado**: os cenários de **webhook Pix** (P1-P7) da matriz estão
marcados como *funcionalidade não existe* — o sistema confirma pagamento de
forma **síncrona** (depósito/`confirmPayment`), sem rota de webhook. Não são
testáveis antes de implementar a funcionalidade; entra no backlog da integração
Pix real.

## Testes de carga (Fase 2/2b)

Os fluxos de dinheiro também são medidos sob **carga real** (Mongo replica set +
transações), em dois eixos — **contenção** (N ops na mesma carteira) e
**distribuída** (N carteiras distintas):

```bash
docker compose build integration-tests        # após mudar src/
node scripts/load-driver.cjs 1 2 5 10          # contenção
node scripts/load-driver.cjs --distributed 1 2 5 10   # distribuída
# ou direto: npm run test:load / npm run test:load:distributed
```

Resultado-chave: a suíte distribuída manteve `rejected = 0` e throughput
**~constante** de 1x a 10x (até 25000 depósitos + 25000 saques + 8000 apostas) —
provando que o teto da suíte de contenção é serialização de documento único, não
capacidade da aplicação. Metodologia completa, tabelas e como reproduzir em
[`LOAD-TESTING.mdx`](./LOAD-TESTING.mdx).

## Teste de repetibilidade (Fase 1)

Antes das medições de carga, a suíte completa foi executada 3× para confirmar
que os resultados não eram circunstanciais: 891 testes unitários herméticos
(3/3 execuções verdes) + 14 de integração real (3/3 verdes), sempre com
`LOAD rejected: 0` (`scripts/load-results/` e `Plano …MVP.md`).

## Troubleshooting

| Sintoma | Causa / solução |
|---|---|
| `port is already allocated` | Existe Mongo/Redis rodando em 27017/6379 na máquina. Pare-o ou rode a infra de teste em outro host. |
| `docker: command not found` | Docker não instalado ou fora do PATH. Instale Docker Engine + Compose v2. |
| `up -d --wait` não funciona | Compose v2 antigo (antes da v2.20). Atualize e rode `docker compose version`. |
| Testes falham conectando no Mongo | Aguarde o `rs0` ficar PRIMARY (log de `npm run test:infra:up`); rode `npm run test:infra:down -v` (reset) via `npm run test:infra:reset` se persistir. |
| Quero ver o estado da infra | `docker compose -f docker-compose.test.yml ps` e `docker compose -f docker-compose.test.yml logs mongo-rs-init`. |
