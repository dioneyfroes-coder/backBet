# Testes, Ambientes e Carga

Guia de todas as suítes, ambientes e cenários críticos cobertos por testes no BackBet.

### Infra de teste

`docker-compose.test.yml` sobe MongoDB (**replica set `rs0`**, anunciado como `mongodb:27017`) + Redis (`redis:6379`) + o serviço `integration-tests`. A suíte roda **dentro da rede Docker**, sem depender de `localhost`/`127.0.0.1`/IP do host — o mesmo caminho usado pelo CI:

```bash
npm run test:integration:full   # build do backbet:test + suíte na rede Docker + teardown
# ou, manualmente:
npm run test:infra:up           # sobe mongodb + redis + mongo-rs-init
npm run test:integration:docker # roda o container integration-tests
npm run test:infra:down
```

> Para inspecionar a infra pelo host, publique as portas via `LAB_BIND_IP` (ver `docker-compose.yml`) — o compose de teste é intencionalmente fechado na rede interna.

> Transações Mongo, locking otimista, workers Bull e idempotência **só fazem sentido** contra o replica set — as suítes de integração/carga exigem esta infra.

## Testes de carga e concorrência

Os testes de carga medem **correção sob contenção**, não throughput:

- **`test:load` (contida)**: N operações concorrentes na **mesma carteira** → valida locking otimista (`version` → `409` + retry), idempotência (`Idempotency-Key`) e retry transitório (`retryTransient.ts`). Provado com 100 saques concorrentes em `WalletConcurrency.test.ts:104-149`.
- **`test:load:distributed` (distribuída)**: N carteiras distintas de forma paralela (eixo horizontal) → valida isolação por agregado e ausência de contenção cruzada.

Regras garantidas sob carga: saldo nunca negativo (FI-01), débito único por saque (FI-04), sem double-spending em apostas simultâneas (B3), WIN com exatamente um crédito (FI-08), CANCEL com exatamente um reembolso (FI-09).

## Teste de crash e backup

`npm run test:crash` (ou `crash.integration.test.ts`) valida o item #15 do plano —
**docker kill nos piores momentos** — cobrindo cada janela do plano (Mongo real, 9/9):

| Caso | Janela de kill (item #15) | O que garante |
|------|---------------------------|---------------|
| C1a | durante transação de **depósito** | rollback total, nada órfão no ledger |
| C1b | durante transação de **aposta** | aposta inexistente e débito+exposição revertidos (risk) |
| C1c | durante transação de **saque** | sem hold órfão, sem request pendente |
| C2 | **após commit / antes da response** | crédito aplicado, `PROCESSING`, reclaim não duplica |
| C3 | **durante retry** | reexecução converge a exatamente 1 crédito |
| C4 | durante **settlement** | prêmio creditado uma única vez |
| C5 | durante **payout** (PSP pago antes do débito) | recuperação consulta o PSP e nunca re-paga |
| C7 | **docker kill REAL (SIGKILL)** do worker durante payout | `PROCESSING` consistente; recuperação conclui 1 único débito |
| C6 | síntese | `reconcileUsers` — wallet/ledger/bet/withdrawal/risk reconciliáveis |

Após cada kill o estado de wallet, ledger, bets, withdrawal e risk é conferido e a
reconciliação financeira (`FinancialReconciliationService`) é executada; o trilho de **audit**
(idempotência/recuperação sem duplicação) é exercitado nos casos C2/C3/C5/C7 e nas
suítes de administração (`admin.audit.integration.test.ts`, `api.integration.*`).

- `npm run test:backup` — exercita `backup:create → restore → validate`; o `backup:drill` automatizado restaura em banco temporário sem tocar o original. Runbook: `docs/BACKUP_RECOVERY.mdx`.

### Multi-worker (item #16)

`npm run test:multiworker` (`multi-worker.integration.test.ts`) sobe **dois workers**
(processos Node reais via `tsx`) disputando o **mesmo payout** sobre Mongo/Redis reais:
o claim `APPROVED → PROCESSING` é atômico, então exatamente um worker toca o PSP; o
vencido retorna sem efeito financeiro. Valida **claim** (1 vence), **payout** (1
chamada ao PSP via marcador compartilhado), **ledger** (1 `WITHDRAWAL_COMPLETED`),
**state transition** (`COMPLETED`) e **idempotência** (uma 3ª entrega não re-paga),
fechando com reconciliação financeira wallet vs ledger.

## Troubleshooting de testes

| Sintoma | Solução |
|---------|---------|
| Testes de integração falham | `npm run test:infra:reset` e confira Mongo/Redis ativos |
| `MongoServerError: Transaction numbers are only allowed...` | Mongo precisa ser replica set (`replicaSet=rs0`) |
| `409` inesperado | Replay de `Idempotency-Key` com payload diferente ou lock otimista — verifique a carteira |
| Cobertura baixa no gate | Rode `npm run test:coverage` local e compare com o limiar do `check` |
