# Backup e Recuperação

O ciclo `backup → destruir ambiente → restore → validar dados` precisa estar **testado e documentado** — é o que esta página cobre, com RPO/RTO e drill automatizado.

## O que é autoritativo

- **MongoDB** é o banco de dados durável do MVP: usuários, carteiras, extrato/ledger, apostas, treasury, risco, idempotência e auditoria. **É o que precisamos recuperar.**
- **Redis** é **efêmero** no MVP (cache e apoio a operações). Se sumir, rebate sozinho — não é coberto pelos backups (a aplicação reconstrói caches).

## Objetivos de recuperação (MVP)

| Métrica | Alvo | Como é garantido |
| --- | --- | --- |
| **RPO** | ≤ 24 h | Backup diário automático (ex.: cron às 03:00) |
| **RTO** | ≤ 60 min | Runbook abaixo + drill `backup:drill`; tempo real medido em maintenance window |
| **Integridade** | A cada 7 dias | `npm run backup:validate -- <dir>` (checksums + contagens) |
| **Retenção** | ≥ 5 anos (operação regulada) / configurável | `--retention` no `backup:create` (default 30 dias; ajustável / `BACKUP_DIR`) |

Para operação regulada (ordem SPA): dados retidos por no mínimo **5 anos**, atualização a cada **24 h**, integridade a cada **7 dias**. Os parâmetros são configuráveis; o MVP parte de 30 dias local.

## Ferramentas (npm scripts)

| Comando | O que faz |
| --- | --- |
| `npm run backup:create` | Dump **lógico** (EJSON) de todas as collections em `BACKUP_DIR/<timestamp>/` + `manifest.json` (contagens e checksums SHA-256). Aceita `--db <nome>` e `--retention <dias>` (purga antigos) |
| `npm run backup:restore -- <dir>` | Restaura um backup. Padrão: **recusa sobrescrever** dados existentes. `--target-db <nome>` restaura em outro banco; `--drop` substitui; valida contagens pós-restore |
| `npm run backup:validate -- <dir>` | Integridade: manifesto legível, arquivos presentes, checksums, JSON/EJSON válido, contagens. `--check-restored <banco>` compara com banco restaurado |
| `npm run backup:drill` | **Drill seguro**: backup do banco real → restore em `backbet_drill_<ts>` (sem tocar o original) → valida → remove. Prova o ciclo no ambiente atual |

> Backups são `.json` com dados de usuário — **nunca commitar `/backups/**`** (`.gitignore`). Grava em `./backups` (ou `$BACKUP_DIR`).

## O ciclo testado

```text
backup ↓ ................ npm run backup:create
destruir ambiente ....... apenas manual (maintenance window), ver runbook
restore ↓ ................ npm run backup:restore -- <dir> [--drop]
validar dados ↓ .......... npm run backup:validate -- <dir> --check-restored <banco>
```

- **Automatizado e seguro**: `backup:drill` exercita o loop completo **sem destruir nada**.
- **Destrutivo**: "destruir o banco de produção" nunca é automatizado — é procedimento agendado com comunicação de janela.

## Runbook: "o banco foi destruído às 3h da manhã"

1. **Pare o tráfego de escrita** (ou faça readonly): `npm run pm2:stop` ou pausa nos workers.
2. **Avalie o dano**: `mongosh --uri "$MONGODB_URI" --eval "db.adminCommand({ ping: 1 })"` e liste databases.
3. **Escolha o backup mais recente validado**: `ls -1t $BACKUP_DIR` e `npm run backup:validate -- ./backups/<timestamp>`.
4. **Restaure**:
   ```bash
   npm run backup:restore -- ./backups/<timestamp>
   # banco parcialmente corrompido:
   npm run backup:restore -- ./backups/<timestamp> --drop
   # inspecionar antes de assumir:
   npm run backup:restore -- ./backups/<timestamp> --target-db backbet_restored
   ```
5. **Valide os dados**: `npm run backup:validate -- ./backups/<timestamp> --check-restored backbet` + `/health` + health-monitor.
6. **Retome o tráfego** e monitore os alertas em `deploy/observability/alerting/alerts.yml`.

**Tempo estimado no MVP**: minutos para volumes pequenos (dump lógico). O RTO de ≤ 60 min se mede no drill com dados reais.

## Rollback de deploy/versão

- Restaure o build anterior (`pm2 reload` / troca de tag do container) e, se o schema mudou, restaure o backup **anterior à migração**:
  ```bash
  npm run backup:restore -- ./backups/<timestamp-antigo> --drop
  ```
- O manifesto registra `createdAt` e `dbName`; compare o timestamp do diretório.

## Disaster recovery (perdeu a máquina inteira)

1. Suba um MongoDB novo (ou reaponte `MONGODB_URI` para backup/S3 gerenciado).
2. Garanta Redis disponível (efêmero).
3. Restaure o backup **mais recente validado** em `backbet` e valide (caminho do runbook).
4. Mantenha uma cópia **fora da máquina** (bucket S3/Blob privado, `mongodump` ou upload dos `.json`) — sem isso, backup é "meia solução".

## Agendamento automático

```cron
# Backup diário + retenção de 90 dias
0 3 * * *  cd /opt/backbet && BACKUP_DIR=/var/backups/backbet npm run backup:create -- --retention 90 >> /var/log/backbet-backup.log 2>&1

# Integridade semanal do backup mais recente
0 4 * * 0  cd /opt/backbet && LATEST=$(ls -1t /var/backups/backbet | head -1) && npm run backup:validate -- /var/backups/backbet/$LATEST >> /var/log/backbet-backup.log 2>&1
```

## Limitações e próximos passos

- Dump lógico carrega cada collection em memória — suficiente para o MVP; bases grandes → `mongodump`/`mongorestore` ou Atlas Continuous Backup + PITR.
- Próximo passo de produção: integrar upload com pipeline S3 + retenção de 5 anos (regulatório) e testar restore em staging periodicamente.
- Alertas de negócio já existentes cobrem indisponibilidade de Mongo/Redis — falhas de infra disparam antes do horário do backup.
