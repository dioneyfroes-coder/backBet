# Core Finance - Documentação

Esta documentação descreve o núcleo financeiro (core/finance) da aplicação: carteira do usuário, serviços relacionados a depósito/saque, value-objects, repositórios e contratos.

## Visão Geral

O core financeiro é responsável por tudo que envolve saldo do usuário: criação de carteiras, depósitos, saques, bloqueio de valores (reservas) e transformações para persistência (DTOs). Ele é projetado para ser independente, testável e consumido por outros domínios (por exemplo, betting).

## Conceitos e Entidades

- Wallet (Carteira): representa o saldo disponível de um usuário, saldo bloqueado (reservas) e a moeda.
	- Campos principais:
		- userId: string
		- balance: number
		- lockedBalance: number
		- currency: string (ex.: BRL, USD, EUR)

## Value Objects

- CurrencyValueObject
	- Tipo suportado: `'BRL' | 'USD' | 'EUR'`.
	- Responsável por validar códigos de moeda.

## Tipos / DTOs

- `IWalletDTO`
	- Forma serializável da `Wallet` para persistência / redes.

- `ICreateWalletDTO`
	- Payload para criar uma carteira: `{ userId: string; currency: string }`.

Os tipos vivem em `src/core/finance/types/wallet.types.ts`.

## Repositórios (contratos)

- `IWalletRepository` (em `src/core/finance/domain/repositories/IWalletRepository.ts`)
	- Responsabilidades:
		- `findByUserId(userId: string): Promise`
		- `save(wallet: Wallet): Promise`
		- `update(wallet: Wallet): Promise`
		- `delete(userId: string): Promise`

Implementações concretas (DB, in-memory, Redis) devem implementar esta interface.

## Serviços

- `WalletService` (em `src/core/finance/domain/services/WalletService.ts`)
	- Métodos:
		- `createWallet(input: ICreateWalletDTO): Promise` - cria carteira para usuário (valida existência e moeda)
		- `deposit(userId: string, amount: number): Promise` - realiza depósito (valida carteira e valor)
		- `withdraw(userId: string, amount: number): Promise` - realiza saque (valida saldo suficiente)

O serviço é intencionalmente pequeno e delega persistência para o repositório.

## Entidade Wallet (detalhes)

- `deposit(amount: number)` → adiciona ao saldo. Valida `amount > 0`.
- `withdraw(amount: number)` → subtrai do saldo. Valida fundos suficientes.
- `lock(amount: number)` → move do `balance` para `lockedBalance` (usar em reservas para apostas/ordens).
- `unlock(amount: number)` → reverte `lock`.
- `toDTO()` → converte para `IWalletDTO`.

## Integração com outros domínios

- O `BetService` (domínio de apostas) consome o `IWalletService` para debitar reservas quando uma aposta é colocada e creditar ganhos na resolução.
- Contratos claros (`IWalletService`, `IWalletRepository`) permitem testar e mockar o comportamento nas camadas superiores.

## Sistema de créditos e pacotes

- A `Wallet` representa créditos (pontos digitais) que imitam dinheiro real dentro do universo BackBet. Cada unidade de `balance` equivale a um ponto que pode ser usado para apostar.
- Os clientes adquirem esses créditos em duas modalidades:
	- **Compra individual:** chama `WalletService.deposit(userId, amount)` e registra uma transação `deposit` com o valor comprado.
	- **Pacotes de créditos:** definem `amount`, `bonus` e `label` (ex.: "Pacote Bronze"). O sistema ainda utiliza `deposit`, mas registra metadados extras para saber se o valor veio de um pacote, facilitando contabilidade e promoções futuras.
- É recomendado criar um modelo adicional (`CreditPackage`, `PurchaseOrder` ou domínio similar) que represente preço, bônus e limites de validade; essa entidade vive em `src/core/finance/domain` ou em um subdomínio específico de vendas.

## Fluxo de apostas com pontos

- Antes de aceitar uma aposta, o `BetService` chama `wallet.lock(stake)` para mover os pontos do `balance` para o `lockedBalance`, garantindo que o valor não possa ser usado em outra aposta enquanto estiver ativa.
- Resolução da aposta:
	- Se perdida ou cancelada: `wallet.unlock(amount)` retorna os pontos reservados para o `balance`.
	- Se vencedora: `wallet.deposit(payout)` credita o prêmio diretamente no `balance`, podendo incluir retornos maiores do que o valor bloqueado.
- Essas operações são orquestradas pelo `WalletService` para garantir que cada mutação passe pelos mesmos gateways de validação e persistência.

## Saques e solicitações administrativas

- O saque é feito mediante uma **solicitação de saque** (ex.: `WithdrawalRequest`) criada pelo usuário com `requestedAmount`. Essa entidade registra `userId`, `amount`, `status` (`pending`, `approved`, `rejected`), `createdAt` e dados bancários.
- Somente após análise manual e aprovação da administração, o sistema executa `wallet.withdraw(amount)` para refletir a saída real de créditos. Esse saque gera uma transação do tipo `withdraw` no histórico.
- Separar o pedido de saque da alteração do saldo evita que chamadas automáticas ao `withdraw` sejam executadas antes da confirmação da transferência financeira real.
- A área financeira pode guardar evidências (comprovantes) e alimentar relatórios de compliance usando o mesmo histórico de transações do `Wallet`.

## Seed de pacotes de crédito

- Há um script de seed (`npm run seed:credit-packages`) que popula o catálogo inicial de pacotes, garantindo que o sistema tenha pacotes padrão quando conectado a Mongo ou a um repositório em memória.
- O script (`src/scripts/seedCreditPackages.ts`) utiliza o `createCreditPackageRepository` para aplicar um `upsert` e registrar as datas de criação/atualização sem gerar duplicatas por código.
- Use esse recurso sempre que iniciar uma nova instância ou quiser repor rapidamente os pacotes promocionais básicos (Bronze, Prata, Ouro e VIP).

## APIs e painel administrativo

- Lista de pacotes: `GET /api/finance/packages` retorna os pacotes ativos com `totalCredits`, `price` e metadados.
- Compra de pacote: `POST /api/finance/packages/:packageId/purchase` chama `PurchaseCreditPackage` e credita o valor total (`base + bônus`). O endpoint devolve a carteira atualizada e os dados do pacote adquirido.
- Solicitação de saque: `POST /api/finance/withdrawal-requests` cria um `WithdrawalRequest` pendente e bloqueia os créditos necessários. Use esse endpoint em conjunto com formulários administrativos para solicitar análise humana.
- Histórico de solicitações: `GET /api/finance/withdrawal-requests` e `PATCH /api/finance/withdrawal-requests/:requestId` expõem o status para o usuário e permitem que um admin aprove ou rejeite a operação.
- A aprovação chama `withdrawLocked` para deduzir os créditos bloqueados após a transferência real; a rejeição chama `unlock` e retorna os pontos ao saldo.

## Exemplo de uso (Fluxo simplificado)

1. Usuário solicita `createWallet({ userId, currency })` → `WalletService` valida e persiste via `IWalletRepository`.
2. Usuário pede `deposit(userId, amount)` → `WalletService` carrega carteira, chama `deposit()` e `update()`.
3. Ao colocar uma aposta, `BetService` chama `walletService.withdraw(userId, stake)` para reservar o valor.
4. Ao resolver a aposta, `BetService` chama `walletService.deposit(userId, payout)` caso o usuário ganhe.

## Observações de design e boas práticas

- Separar contratos (interfaces) das implementações facilita testes e troca de backend (por exemplo, trocar in-memory por TypeORM).
- Toda lógica que altera estado da carteira (balance / lockedBalance) fica dentro da entidade `Wallet` para centralizar validações.
- O serviço (`WalletService`) é responsável por orquestrar validações de alto nível e persistência.

## Como testar

- Testes unitários das entidades (`Wallet`) e value-objects (`CurrencyValueObject`) devem cobrir cenários de borda: depósitos negativos, saques maiores que o saldo, lock/unlock inconsistentes.
- Testes do `WalletService` devem mockar `IWalletRepository` e validar chamadas a `save`/`update` e lançamentos de erro.

## Próximos passos sugeridos

1. Implementar adaptadores de persistência: um repositório em memória para teste e um adaptador com banco (TypeORM ou Prisma).
2. Adicionar eventos de domínio para operações críticas (ex.: `WalletCredited`, `WalletDebited`).
3. Implementar limites anti-fraude e validações de compliance quando necessário.
