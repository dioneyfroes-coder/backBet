# Core Finance

> Camada responsável por créditos dos usuários (balance/balanceCents + lockedBalance/lockedBalanceCents), pacotes promocionais e solicitações de saque. Tudo é construído sobre DDD, value objects e use cases reutilizáveis por Auth, Betting e painéis administrativos.

## Domínio e entidades

### Wallet (`src/core/finance/domain/entities/Wallet.ts`)
- Mantém `balance` (reais), `balanceCents` (centavos para persistência), `lockedBalance` / `lockedBalanceCents`, `currency` e histórico de `Transaction`.
- Expõe operações atômicas: `deposit`, `withdraw`, `lock`, `unlock`, `withdrawLocked`, todas validadas por `Money` (value object compartilhado) e lançando `DomainError` (`WALLET_INVALID_AMOUNT`, `WALLET_INSUFFICIENT_FUNDS`, etc.).
  - **Importante:** qualquer tentativa de saque (`withdraw`) ou aposta com valor zero ou negativo é rejeitada com erro de validação.
- `recordTransaction` agora aceita `TransactionContext` com `description` + `metadata` (ex.: `channel: "PIX"`, referencias do gateway), persistindo o payload para auditoria mesmo quando usamos provedores simulados.

### Transaction (`src/core/finance/domain/entities/Transaction.ts`)
- DTO-friendly (`toDTO`) usado pelo histórico paginado (`IWalletRepository.getHistory`).
- Não há persistência própria; cabe ao repositório escolher salvar em Mongo/Mongoose ou manter em memória.

### CreditPackage (`src/core/finance/domain/entities/CreditPackage.ts`)
- Define pacotes com `baseAmountCents`, `bonusAmountCents`, `totalCreditsCents`, `priceCents` e `isActive`. Getters em reais (`baseAmount`, `bonusAmount`, `totalCredits`, `price`) são derivados dividindo por 100.
- Usado para `PurchaseCreditPackage`, retornando `creditPackage.toDTO()` para front e painel.

### WithdrawalRequest (`src/core/finance/domain/entities/WithdrawalRequest.ts`)
- Representa todo saque manual, com `status` (`PENDING`, `APPROVED`, `REJECTED`), `ApprovalLog` e validação de valor.
- `approve`/`reject` adicionam logs e garantem que cada solicitação só seja processada uma vez.

### CurrencyValueObject (`src/core/finance/domain/value-objects/Currency.ts`)
- Aceita apenas `BRL | USD | EUR`. Valores inválidos disparam `DomainError('CURRENCY_INVALID_CODE')` e são convertidos para `AppError` via mapper.

## Sistema monetário (padrão: BRL)

- O valor monetário em todo o core financeiro é representado pelo value object `Money` (`src/core/shared/domain/value-objects/Money.ts`). Ele garante que qualquer depósito, saque, bloqueio ou transação:
  - use um número positivo ≥ 0 com duas casas decimais (internamente `Money.amount` em reais);
  - respeite sempre a mesma moeda (`Money.currency`). Qualquer tentativa de somar/subtrair moedas diferentes dispara `DomainError('MONEY_CURRENCY_MISMATCH')` e o mapper `WalletErrorMapper` converte isso em um `AppError` 400 que chega claro ao front-end;
  - envolva apenas `SUPPORTED_CURRENCIES`, que hoje inclui `['BRL', 'USD', 'EUR']` e permite modularmente adicionar novos códigos no futuro sem quebrar a lógica de domínio.
  - `Money.getCents()` retorna o valor em centavos inteiros (para persistência); `Money.fromCents(cents, currency)` cria um `Money` a partir de centavos inteiros;
  - A persistência (Mongoose) armazena valores em centavos inteiros (`balanceCents`, `amountCents`, `exposureCents`, etc.) e converte de volta via `Money.fromCents()` ao hidratar. O domínio e a API trabalham em reais (decimal).
- No momento operamos exclusivamente em `BRL`. O onboarding, as apostas e as integrações Pix usam `CurrencyValueObject` com valor padrão `BRL`, e o backend fornece sempre `currency: 'BRL'` nas respostas (`Wallet.toDTO()`, `WalletDepositResponse`, `WalletWithdrawResponse`, etc.).
- Para suportar outra moeda futuramente: basta adicionar o código desejado a `SUPPORTED_CURRENCIES`, garantir que o `CurrencyValueObject` aceite o novo código, configurar os tamanhos mínimos/max e traduzir as taxas em `appConfig.wallet.limits` se necessário. Essa modularidade preserva todos os métodos `Money.add/subtract/multiply` sem mudanças.

## Boas práticas para consumir o sistema monetário no frontend

1. **Use os dados oficiais da resposta ao invés de recalcular o saldo.** A API retorna `{ data: { balance, lockedBalance, currency } }` para `/api/wallets/me` (valores em reais, não centavos). Confie nesses valores e apenas formate com a `currency` enviada.
2. **Formate com `Intl.NumberFormat('pt-BR', { style: 'currency', currency })`.** Isso garante corretas casas decimais e separador de milhares. Nunca multiplique ou divida os valores exibidos para obter um novo saldo — o backend já faz isso com o `Money` value object e registra transações.
3. **Envie valores como números decimais com duas casas (ex.: `10.00`).** O backend valida `amount > 0` e aplica `Money` antes de qualquer alteração. Strings ou formatos com vírgula serão rejeitados pelo Zod/`CreateWithdrawalRequestDTO`, portanto use sempre o ponto (`.`) como separador decimal nas requisições. Internamente o valor é convertido para centavos (ex.: `10.00` → `amountCents: 1000`) antes de persistir.
4. **Considere o campo `lockedBalance` ao mostrar disponibilidade.** O saldo livre é `balance - lockedBalance`. Atividades como `coin-flip` primeiro chamam `wallet.withdraw(userId, wager)` e só depois registram o resultado; nenhum outro campo precisa ser atualizado manualmente.
5. **Mantenha front-end desacoplado da moeda concreta.** Embora hoje seja `BRL`, sempre consulte `currency` no payload (por exemplo, `wallet.currency` no histórico) para evitar suposições. Quando outras moedas forem liberadas, a API continuará informando o código correto graças ao mesmo `Money.toString()` usado internamente.

### Tipagem e formatação recomendadas

```ts
// tipos compartilhados no front-end (ex.: src/types/finance.ts)
export type MoneyAmount = number; // deve vir com duas casas decimais (ex.: 10.00)
export type CurrencyCode = 'BRL';

export interface WalletSnapshot {
  userId: string;
  balance: MoneyAmount;      // reais (decimal) — API response
  balanceCents: number;       // centavos (inteiro) — persistência
  lockedBalance: MoneyAmount;
  lockedBalanceCents: number;
  currency: CurrencyCode;
}

export interface WalletHistoryTransaction {
  id: string;
  type: 'deposit' | 'withdraw' | 'lock' | 'unlock' | 'withdraw_locked';
  amount: MoneyAmount;
  currency: CurrencyCode;
  createdAt: string; // ISO 8601
}
```

Para formatar valores no front em BRL, use `Intl.NumberFormat`: 

```ts
const formatter = new Intl.NumberFormat('pt-BR', {
  style: 'currency',
  currency: 'BRL',
  minimumFractionDigits: 2,
});

formatter.format(wallet.balance); // wallet.balance retorna reais (não centavos)
```

Para enviar um saque/deposito, mantenha um objeto simples em JSON e use o ponto como separador decimal:

```ts
await fetch('/api/wallets/withdraw', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({
    amount: 10.0, // número em reais (decimal), convertido para amountCents internamente
    currency: 'BRL',
    pixKey: user.pixKey,
    description: 'Coin flip wager',
  }),
});
```

Repare que `amount` sempre é um `number` em reais com duas casas decimais. O backend converte internamente para centavos (`amountCents`) ao persistir. Se precisar gerar o valor dinamicamente, calcule no JavaScript e use `Number(wager.toFixed(2))` antes de enviar para evitar imprecisão de ponto flutuante.

Essa abordagem documenta o fluxo monetário, garante consistência e mantém a porta aberta para adicionar novas moedas sem refatorar cada endpoint/backoffice.

## Serviços e repositórios

- `WalletService`: orquestra verificações e delega persistência para `IWalletRepository`. Expõe `createWallet`, `deposit`, `withdraw`, `lock`, `unlock`, `withdrawLocked`, `getHistory`.
- `IWalletService`: contrato consumido por `BetService` para debitar/creditar apostas sem acoplar a implementação concreta.
- `CreditPackageService`: lista/recupera pacotes (via `ICreditPackageRepository`) e valida existência antes da compra.
- `WithdrawalRequestService`: sincroniza `WithdrawalRequest` com operações de carteira (lock durante a criação, `withdrawLocked` ou `unlock` ao aprovar/rejeitar) e possui validações anti saldo negativo.
- `WalletRepository`, `CreditPackageRepository`, `WithdrawalRequestRepository`: implementações in-memory para dev/teste.
- `src/infrastructure/persistence/factory.ts`: carrega versões Mongoose (`MongooseWalletRepository`, etc.) quando `USE_MONGOOSE_PERSISTENCE=true`, mantendo a mesma interface para rotas Auth/Wallet/Finance.

## Casos de uso principais

| Use case | Responsabilidade | Entrada | Saída |
|----------|------------------|---------|-------|
| `GetWallet` | Busca carteira do usuário e propaga `null` se inexistente | `userId` | `Wallet | null` |
| `Deposit` / `Withdraw` | Orquestram Pix charge/payout antes de tocar a carteira | `Deposit`: `userId`, `amount`, `currency`, `description?` – `Withdraw`: `userId`, `amount`, `currency`, `pixKey?`, `description?` (usa a chave padrão do usuário quando ausente) | `Deposit` retorna `{ wallet, pixCharge, pixConfirmation }`; `Withdraw` retorna `{ wallet, pixPayout }` |
| `GetHistory` | Retorna histórico paginado (`limit`, `offset`) | `userId`, `limit`, `offset` | `{ transactions, total }` |
| `ListCreditPackages` | Lista pacotes ativos | — | `CreditPackage[]` |
| `PurchaseCreditPackage` | Deposita `base + bônus` após validar pacote | `userId`, `packageId` | `{ creditPackage, wallet }` |
| `RequestWithdrawal` / `GetWithdrawalRequests` | Cria e lista `WithdrawalRequest` bloqueando saldo. A exigência de senha depende do flag global `WALLET_REQUIRE_WITHDRAW_PASSWORD` ou da preferência do próprio usuário (`requireWithdrawPassword`); quando exigida, comparamos a senha enviada com o hash armazenado. | `userId`, `amount`, `currency`, `notes?`, `password?` | Entidade(s) de saque; retorna 403 quando a senha é exigida e inválida/ausente. |
| `ProcessWithdrawalRequest` | Aprova/rejeita e executa `withdrawLocked`/`unlock` | `requestId`, `adminId`, `action`, `notes?` | `WithdrawalRequest` atualizado |

Todos envolvem `executeWithWalletErrorMapping`, traduzindo `DomainError` em `AppError` com status HTTP coerentes.

## Fluxos ponta a ponta

### Criação de carteira no onboarding
1. `RegisterUser.execute` cria usuário e invoca `WalletService.createWallet` com moeda default (`BRL`).
2. Em caso de erro (`WALLET_ALREADY_EXISTS`), o mapper devolve 409 e o fluxo de cadastro é interrompido.

### Compra de pacote de créditos
1. `POST /api/finance/packages/:packageId/purchase` valida params (`CreditPackagePurchaseDTO`).
2. `PurchaseCreditPackage` busca o pacote, soma `base + bonus` e chama `WalletService.deposit`.
3. `flushWalletCache(userId)` limpa `wallet:balance` e `wallet:history` para refletir o novo saldo imediatamente.

### Solicitação e aprovação de saque
1. `POST /api/finance/withdrawal-requests` valida `CreateWithdrawalRequestDTO`, chama `RequestWithdrawal` que bloqueia o valor (`wallet.lock`).
2. Admins usam `PATCH /api/finance/withdrawal-requests/:id` para aprovar (`withdrawLocked`) ou rejeitar (`unlock`).
3. Cada decisão gera `ApprovalLog` e dispara `flushWalletCache`.

### Integração Pix (mock)
1. Rotas `/api/wallets/deposit|withdraw` chamam `PixProviderPort` antes de persistir a transação.
2. O adapter atual (`MockPixProvider`) gera QR Codes/payouts determinísticos e confirma o pagamento imediatamente, propagando os campos para `wallet.recordTransaction(...metadata)`.
3. Os responses expõem `pix.*` para que o front exiba referência, status e provider. Em produção basta criar outro adapter e mudar `PIX_PROVIDER` sem modificar controllers/use cases.
4. `PIX_ENABLE_DEPOSITS` / `PIX_ENABLE_WITHDRAWALS` podem ser usados como kill switches: quando `false`, os controllers retornam `503 SERVICE_UNAVAILABLE` antes de chamar o Pix ou tocar na carteira.

### Integração com Betting
- `BetService.placeBet` usa `IWalletService.withdraw` para reservar stake; cancelamentos devolvem via `deposit` e vitórias pagam `wallet.deposit(potentialReturn)`.
- Como `BetService` fala com o contrato e não com o repositório, é fácil trocar a implementação (e.g., Mongoose) sem tocar no domínio de apostas.

### Coin-flip e limites de aposta
- O jogo de coin-flip é configurado em `appConfig.games.coinFlip` com variáveis de ambiente (`GAME_COINFLIP_*`). Por padrão ele está **habilitado**, aceita apostas entre `minBet=1` e `maxBet=500` (BRL) e aplica um `payoutMultiplier=1`, isto é, o prêmio pago ao vencedor é `wager × payoutMultiplier`. A qualquer momento esses valores podem ser ajustados sem deploy via `.env`/secret manager.
- A variação do valor apostado depende exatamente desses limites (`GAME_COINFLIP_MIN_BET` e `GAME_COINFLIP_MAX_BET`), então o frontend deve permitir apenas números dentro do intervalo informado pelo backend (o próprio `GameController` expõe esses campos no `/api/games/coin-flip/config`).
- Existe também `GAME_COINFLIP_FIXED_WIN`: quando definido e positivo, o jogo ignora `wager × multiplier` e paga sempre esse valor fixo, mantendo o `metadata.source` marcado como `fixed-win` nos logs. Isso costuma ser usado para campanhas promocionais sem alterar o multiplicador base.
- Os detalhes do multiplicador e do intervalo aparecem na resposta de `/api/games/coin-flip/config` e são utilizados pelo `CoinFlipGameService` (arquivo `src/core/game/domain/services/CoinFlipGameService.ts`) para calcular `payoutAmount = Number((wager × payoutMultiplier).toFixed(2))` antes de registrar a transação e afetar o `Wallet` do usuário.

## HTTP API

### Rotas de carteira (`src/infrastructure/api/routes/walletRoutes.ts`)

| Método | Caminho | Proteção | Cache/Rate limit | Observações |
|--------|---------|----------|------------------|-------------|
| `GET` | `/api/wallets/me` | `protectedRoute` | `cacheWalletBalanceMiddleware` (Redis) | Retorna `wallet.toDTO()` sempre com `Cache-Control: no-store` (sem ETag) e 404 se carteira não existir.
| `POST` | `/api/wallets/deposit` | `protectedRoute` | `createRouteRateLimiter` usando `WALLET_DEPOSIT_RATE_LIMIT_*` | Payload `DepositDTO`; dispara `flushWalletCache`.
| `POST` | `/api/wallets/withdraw` | `protectedRoute` | Rate limit `WALLET_WITHDRAW_RATE_LIMIT_*` | Usa `WithdrawDTO`; aceita `pixKey` opcional e cai para a chave padrão do usuário antes de rejeitar o saque.
| `GET` | `/api/wallets/history` | `protectedRoute` | `cacheWalletHistoryMiddleware` (cache por `limit/offset`) | Responde `{ transactions, pagination }`.

### Rotas financeiras (`src/infrastructure/api/routes/financeRoutes.ts`)

| Método | Caminho | Proteção | Observações |
|--------|---------|----------|-------------|
| `GET` | `/api/finance/packages` | `protectedRoute` | Lista pacotes ativos com datas em ISO 8601.
| `POST` | `/api/finance/packages/:packageId/purchase` | `protectedRoute` | Realiza depósito `base+bonus`, retorna carteira atualizada e pacote.
| `POST` | `/api/finance/withdrawal-requests` | `protectedRoute` | Cria solicitação de saque e bloqueia saldo.
| `GET` | `/api/finance/withdrawal-requests` | `protectedRoute` | Lista solicitações do usuário autenticado.
| `PATCH` | `/api/finance/withdrawal-requests/:requestId` | `protectedRoute` | Processa aprovação/rejeição. (Para uso administrativo; autenticação delegada a `AuthMiddleware`.)

## DTOs e validação

- `DepositDTO` / `WithdrawDTO` (`src/infrastructure/api/dtos/WalletDTOs.ts`): exigem `amount > 0`, `currency ∈ {BRL,USD,EUR}` e `description?`. `pixKey` passa a ser opcional; quando não vier no payload, o controller busca a chave salva no perfil do usuário antes de negar o fluxo.
- `FinanceDTOs.ts` contém: `CreditPackagePurchaseDTO`, `CreateWithdrawalRequestDTO` (mínimo 0.01), `ProcessWithdrawalRequestDTO`, `CreditPackageResponseDTO`, `WithdrawalRequestResponseDTO`.
- Todos os controllers usam `BaseController.validateSchema` para retornar `AppError` padronizado (`code`, `message`, `status`).

### Esquemas sugeridos para o frontend (Zod)

O backend sempre envolve payloads em `{ success, data?, error?, meta }`. Abaixo estão sugestões de schemas para as rotas mais usadas pelo app:

```ts
import { z } from 'zod';

const MetaSchema = z.object({
  timestamp: z.string(),
  requestId: z.string().optional(),
});

// Schema de persistência (Mongoose) usa nomes diferentes:
// balanceCents, lockedBalanceCents (inteiros em centavos)
const WalletSnapshotSchema = z.object({
  userId: z.string().uuid(),
  balance: z.number(),
  lockedBalance: z.number(),
  currency: z.enum(['BRL', 'USD', 'EUR']),
});

export const WalletBalanceResponseSchema = z.object({
  success: z.literal(true),
  data: WalletSnapshotSchema,
  meta: MetaSchema,
});

const PixChargeSchema = z.object({
  chargeId: z.string(),
  reference: z.string(),
  status: z.string(),
  provider: z.string(),
  qrCode: z.string(),
  expiresAt: z.string(),
  confirmedAt: z.string().nullable().optional(),
});

export const WalletDepositResponseSchema = z.object({
  success: z.literal(true),
  data: z.object({
    message: z.string(),
    pix: PixChargeSchema,
    wallet: WalletSnapshotSchema,
  }),
  meta: MetaSchema,
});

const PixPayoutSchema = z.object({
  payoutId: z.string(),
  reference: z.string(),
  status: z.string(),
  provider: z.string(),
  processedAt: z.string().nullable().optional(),
});

export const WalletWithdrawResponseSchema = z.object({
  success: z.literal(true),
  data: z.object({
    message: z.string(),
    pix: PixPayoutSchema,
    wallet: WalletSnapshotSchema,
  }),
  meta: MetaSchema,
});

export const ApiErrorSchema = z.object({
  success: z.literal(false),
  error: z.object({
    code: z.string(),
    message: z.string(),
    details: z.record(z.string()).optional(),
  }),
  meta: MetaSchema,
});
```

> Se quiser validar `pix.status` com enums específicos, use `z.enum(['PENDING','PAID','EXPIRED','FAILED'])` para depósitos e `z.enum(['PROCESSING','COMPLETED','FAILED'])` para saques. Como provedores reais podem adicionar novos estados, mantenha `z.string()` ou `z.union([z.enum(...), z.string()])` quando for prudente.

## Cache e consistência

- `redisClient` lê `cacheConfig` (`REDIS_URL`, TTLs) e expõe helpers `cacheWalletBalance`, `cacheWalletHistory` e `flushWalletCache`.
- `cacheMiddleware` intercepta respostas, salva JSON e devolve hits rapidamente (inclusive com query params em `/history`).
- Sempre que a carteira muda (`deposit`, `withdraw`, compras de pacote, criação/processamento de saque) os controllers chamam `flushWalletCache` para invalidar `wallet:balance` e `wallet:history` do usuário.

## Configurações e rate limits

- **Persistência:** `USE_MONGOOSE_PERSISTENCE=true` liga repositórios Mongo (`MongooseWalletRepository`, etc.).
- **Cache:** `CACHE_ENABLED`, `CACHE_TTL_SECONDS`, `CACHE_USER_BALANCE_TTL_SECONDS`, `CACHE_WALLET_HISTORY_TTL_SECONDS`, `REDIS_URL` controlam Redis.
- **Wallet rate limit:** `WALLET_DEPOSIT_RATE_LIMIT_{WINDOW_MS,MAX,MESSAGE}` e `WALLET_WITHDRAW_RATE_LIMIT_{WINDOW_MS,MAX,MESSAGE}` abastecem `createRouteRateLimiter`.
- **Wallet limits & Pix toggles:** `WALLET_MIN_DEPOSIT` (default 1 BRL) e `WALLET_MIN_WITHDRAW` (default 100 BRL) alimentam `DepositDTO`/`WithdrawDTO`, enquanto `PIX_ENABLE_DEPOSITS` e `PIX_ENABLE_WITHDRAWALS` permitem pausar os fluxos sem desligar o serviço inteiro.
- **Tesouraria:** `TREASURY_MIN_PRIZE_RATIO`, `TREASURY_MAX_PRIZE_RATIO` e `TREASURY_TARGET_PRIZE_RATIO` definem a faixa/objetivo de rebalanceamento (o alvo é sempre clampado dentro da faixa), com `TREASURY_MIN_PROFIT_BUFFER`, `TREASURY_MAX_TRANSFER_PER_RUN` e `TREASURY_REBALANCE_INTERVAL_MS` controlando o job automático.
  
## Tesouraria da casa

- **HouseWallet:** o módulo da carteiras da casa vive em `src/core/treasury/domain/entities/HouseWallet.ts`. Ele mantém dois `Money` separados (`profit` e `prizeReserve`) e persiste como `profitBalanceCents` e `prizeReserveBalanceCents` (inteiros em centavos) no Mongoose schema. O `HouseTreasuryService` registra lucratividade, transfer entre reservas e rebalanceamento do alvo de prêmio (`targetPrizeRatio`). Cada movimentação gera um `TreasuryLedgerEntry` (apenas 50 entradas retidas) com `type`, `amountCents`, `currency`, `description` e `metadata` (ex.: `source`, `referenceId`, `actorId`).
- **Fluxo de apostas:** quando o `BetService` é executado, o stake sai da carteira do usuário via `WalletService.withdraw` e só depois o retorno (quando houver) é depositado de volta. O spread entre o valor pago e o valor devolvido entra como lucro (`RecordTreasuryProfit`) na carteira da casa antes de ser empurrado para `prizeReserve` se o buffer estiver alto demais. Isso garante que o percentual da casa fique separado do saldo do usuário e do dinheiro destinado a prêmios.
- **Valores iniciais:** usamos o script `npm run seed:treasury -- 5000 "Seed inicial"` para registrar um lucro teórico de R$5.000 na carteira da casa e garantir que a parada comece com `profitBalanceCents`=500000, `prizeReserveBalanceCents`=0 (ou em reais: `profitBalance`=5000, `prizeReserveBalance`=0). O walletId padrão é `house-primary` e sempre opera em `BRL` a menos que você sobrescreva `appConfig.treasury.currency`.
- **Monitoramento e investigação:** o admin pode chamar `/api/admin/treasury/summary` (GET) para ver `profitBalance`/`profitBalanceCents`, `prizeReserveBalance`/`prizeReserveBalanceCents`, `totalBalance`/`totalBalanceCents` e o objeto `config` (`targetPrizeRatio`, `minProfitBuffer`, `maxTransferPerRun`). Há também `/api/admin/treasury/ledger?limit=25` para listar as entradas (`type`, `amount`, `description`, `createdAt`, `metadata`). Rebalanceamentos manuais (`POST /api/admin/treasury/rebalance`) ou movimentações manuais (`POST /api/admin/treasury/profit`, `/profit-to-prize`, `/prize-to-profit`) passam pelo mesmo service e aparecem no ledger com `source`/`context` no metadata. Todas essas rotas exigem `protectedRoute` + `requireAdminRole`, de modo que só painéis administrativos/autenticados com escopo elevam estado.
- **Como checar o saldo atual:** mesmo que você tenha semeado 5k, o valor exato muda conforme operadores registram lucros e rebalanceamentos. Use o summary acima (`GET /api/admin/treasury/summary`, o controller responde `{ summary, config }`) para ver o valor atualizado; o campo `totalBalance` corresponde ao que chamamos de "saldo da casa" atualmente disponível. O mesmo endpoint também informa se o `targetPrizeRatio` (geralmente 0.6) está sendo respeitado.
- **Finance:** `AUTH_*` e `RATE_LIMIT_*` globais ainda protegem rotas pois herdam o middleware padrão definido em `app.ts`.

## Seeds e dados iniciais

- Rode `npm run seed:credit-packages` para criar pacotes Bronze/Prata/Ouro/VIP (`src/scripts/seedCreditPackages.ts`).
- O script reutiliza `createCreditPackageRepository`, portanto persiste tanto em memória quanto em Mongo (se `USE_MONGOOSE_PERSISTENCE=true`).
- Use esse seed sempre que subir um novo ambiente para garantir catálogos consistentes e evitar compras com pacote inexistente.

### Script para consultar saldo direto no banco

- `npm run wallet:balance -- --userId <uuid>` imprime o snapshot da carteira diretamente do repositório configurado (Mongoose ou in-memory). Use `--email <user@dominio.com>` como alternativa para descobrir o `userId` automaticamente.
- Adicione `--history 5` (ou outro número) para listar as últimas transações retornadas por `IWalletRepository.getHistory`.
- O script conecta/desconecta do MongoDB apenas quando `USE_MONGOOSE_PERSISTENCE=true`, permitindo depurar rapidamente valores reais sem depender da API HTTP.

## Observabilidade e troubleshooting

- `executeWithWalletErrorMapping` converte `DomainError` → `AppError` com status (ex.: `WALLET_ALREADY_EXISTS` → 409, `WALLET_NOT_FOUND` → 404, `WALLET_INVALID_AMOUNT` → 400).
- Logs relevantes:
  - `FinanceController` loga falhas ao limpar cache.
  - `RedisClient` incrementa métricas (`hits`, `misses`, `writes`, `errors`) e emite `console.warn` quando operações falham.
- Problemas comuns:
  - `NOT_FOUND Wallet not found` → certifique-se de que o fluxo de cadastro criou a carteira (recrie com `WalletService.createWallet`).
  - `BAD_REQUEST Saldo insuficiente` em saques/withdraw → verifique `lockedBalance` e histórico.
  - `CACHE_DISABLED` (implícito) → quando `CACHE_ENABLED=false`, as rotas continuam funcionando sem Redis.
