# Observabilidade

Como o BackBet expõe logs, sinais operacionais, health checks, tracing e alertas — e como ele **se protege** quando dependências degradam.

## Endpoints de saúde

| Endpoint | O que responde |
|----------|----------------|
| `GET /health` | Healthcheck simples (`up`) |
| `GET /health/cache` | Estado do cache Redis (hits/misses/writes/errors) |
| `GET /readiness` | Prontidão geral: pings em Mongo/Redis atualizam `dependencyHealthSnapshot`; dependência caiu → `503`/`ready=false` |
| `GET /api/docs` | Swagger UI |

Uso típico: load balancers/proxies consomem `/health/cache` e `/readiness` para tirar instâncias problemáticas do pool.

## Logs estruturados (JSON)

Cada log é uma linha JSON para `stdout`/`stderr` (e, opcionalmente, `logs/backbet.log`) com campos obrigatórios `level`, `event`, `timestamp` e correlação `requestId`/`userId` propagada por `AsyncLocalStorage` (`src/shared/observability/requestContext.ts`).

Eventos automáticos (`src/infrastructure/api/ApiServer.ts`):

| Evento | Nível | Quando |
|--------|-------|--------|
| `request_start` | info | Entrada no `loggingMiddleware` (`method`, `path`, `ip`, `userId`) |
| `request_end` | info | `res.finish` (`status`, `durationMs`, `contentLength`) |
| `request_error` | error | Handler global (`code`, `statusCode`, `details`) |
| `request_healthcheck` | info | Handlers `/health*` |
| `observability_toggle_state` | info | Toggles `OBS_*` em runtime |
| `readiness_dependency` | warn/error | Dependência caiu em `/readiness` |
| `startup` | info | Boot do ApiServer |

```json
{ "level": "info", "event": "request_end", "timestamp": "2026-09-20T12:00:00.000Z",
  "requestId": "req-...", "method": "POST", "path": "/api/v1/bets",
  "status": 201, "durationMs": 128.4, "userId": "user_2YQk" }
```

- **Correlação**: `requestId` de `X-Request-ID` ou gerado; `userId` injetado após auth; `traceId` quando `TRACING_ENABLED=true`.
- **Arquivo**: `LOG_FILE_ENABLED` (default `true` em prod), `LOG_FILE_PATH` (`logs/backbet.log`), rotação `LOG_FILE_MAX_SIZE_MB` (20) / `LOG_FILE_MAX_FILES` (5).
- **Regras**: nunca logar segredos/tokens/documentos completos (mascarar); preferir snake_case curto e estável para `event`; serializar manualmente com `JSON.stringify`.

## Métricas e tracing

- **`/metrics`**: responde `410 Gone` por padrão; só é ativo com `OBS_ENABLE_PROMETHEUS=true` (uso opcional em dev).
- **Tracing**: OpenTelemetry (Express/Mongoose/ioredis instrumentation) quando `TRACING_ENABLED=true`, exportado via OTLP (`OTEL_EXPORTER_OTLP_*`).
- **Snapshots** (leituras de correlação de logs): `cacheMetricsSnapshot`, `resilienceMetricsSnapshot`, `dependencyHealthSnapshot` — alimentam PM2 WebUI, alertas e `/readiness`.
- **Stack opcional**: `docker-compose.observability.yml` (Prometheus + Grafana + Collector) pode ser usada quando o `/metrics` estiver ativo; a operação padrão do MVP usa PM2 WebUI + alertas.

## Processos (PM2)

`ecosystem.config.cjs`: modo `cluster` (`instances = PM2_INSTANCES || cpus - 1`), reinício por memória (`max_memory_restart: 512M`), logs em `logs/`.

```bash
npm run build && pm2 start ecosystem.config.cjs --env production
pm2 reload backbet --env production   # zero downtime
```

| Script | Uso |
|--------|-----|
| `npm run pm2:webui:start` / `:stop` / `:status` / `:logs` | Painel PM2 WebUI (`PM2_WEB_PORT`, default 9615) |
| `npm run pm2:health:start` / `:stop` | Processo `health-monitor` (`scripts/health-monitor.cjs`) |

- **PM2 WebUI**: proteja com túnel SSH/VPN/proxy autenticado; `PM2_WEB_USERNAME`/`PM2_WEB_PASSWORD`.
- **health-monitor**: `HEALTH_MONITOR_BASE_URL`, `HEALTH_MONITOR_INTERVAL`, `HEALTH_MONITOR_RECIPIENTS`, `SMTP_USERNAME`/`SMTP_PASSWORD`; `HEALTH_MONITOR_DRY_RUN=true` evita envio real; `HEALTH_MONITOR_RUN_ONCE=true` roda fora do PM2.
- `APP_NAME` = produto; `SERVICE_NAME` = instância operacional (alimenta `OTEL_SERVICE_NAME` e métricas).

## Alertas

- Regras em `deploy/observability/alerting/alerts.yml` (12 regras) cobrem indisponibilidade de Mongo/Redis etc.
- Alertas por e-mail: `OBS_ENABLE_EMAIL_ALERTS=true` + `SMTP_*`.

## Resiliência (proteção contra dependências)

1. **Rate limiting** global/por rota — contém spikes em auth/deposit/bets; propaga headers `RateLimit-*`.
2. **Fallback de auth em dev** — `ALLOW_DEV_BEARER_BYPASS=true` tolera provedor de identidade indisponível localmente.
3. **Fábrica de repositórios** — alterna para in-memory se o Mongo oscilar (apenas dev/test; em produção o `USE_MONGOOSE_PERSISTENCE=true` é o esperado).
4. **Cache**: se o Redis cai, leituras fazem fallback direto ao Mongo; `CACHE_ENABLED=false` desliga o cache em emergência.
5. **Readiness defensivo** — dependência `down` → `503`/`ready=false`, tirando a instância do pool.
6. **Retry/circuit breaker** — `src/shared/resilience/*`; retry transitório com backoff em `retryTransient.ts` para conflitos (`409`) e write-conflicts do Mongo (`112`/`TransientTransactionError`).
7. **Tolerância a falha em workers** — saques/SIGAP/auditoria com retry e idempotência (ver `docs/Finance_docs.mdx` e `docs/SIGAP_CONFORMIDADE.mdx`).

## Checklist rápido

- `GET /health`, `/health/cache`, `/readiness` respondendo e com `requestId` em todos os logs.
- Sem `request_error` em picos; `readiness_dependency` sem `down` sustentado.
- `pm2 monit` (ou WebUI) estável, sem restarts em cascata.
- Segredos nunca em logs; `npm run check:secrets` verde.
