# BackBet API

> Os módulos `auth`, `user`, `wallet`, `finance`, `bet`, `events`, `games` e `admin` são montados pelo `ApiServer` em `/api/**`, compartilhando o mesmo container de dependências (repositórios, serviços de domínio, cache hooks, Passport/JWT, rate limiters e métricas). Este guia resume os contratos expostos hoje.

## Base URLs

| Ambiente | URL base | Docs interativos |
|----------|----------|------------------|
| Desenvolvimento | `https://backbet.onrender.com/api` | `https://backbet.onrender.com/api/docs` |
| Produção (exemplo) | `https://backbet.onrender.com/api` | `https://backbet.onrender.com/api/docs` |

> A especificação completa está disponível em `/api/docs.json` (OpenAPI 3.1) e usa os mesmos `servers` com prefixo `/api`. Todos os exemplos usam versão v1.

## Autenticação e cabeçalhos

- `Authorization: Bearer <token>` é obrigatório nas rotas marcadas como protegidas (`protectedRoute`).
- Tokens aceitos:
  - JWT emitido pelo provedor de identidade configurado (produção). Em ambientes que usam `passport-jwt`, o backend valida tokens via Passport middleware.
  - JWT local gerado pelo `JwtService` (`/auth/login`, `/auth/refresh`).
  - Bypass de desenvolvimento: defina `ALLOW_DEV_BEARER_BYPASS=true` e envie `Authorization: Bearer <userId>` para forçar a sessão.
- `Content-Type: application/json` em `POST` / `PATCH`.
- Cada requisição recebe `X-Request-ID`; o mesmo valor é logado e propagado via `AsyncLocalStorage` (vide `docs/OBSERVABILITY.mdx`).

## Resposta padrão e erros

Todos os controllers herdam `BaseController`, produzindo envelopes consistentes:

```json
{
  "success": true,
  "data": { "message": "...", "payload": { /* ... */ } },
  "meta": { "timestamp": "2025-11-23T15:00:00.000Z", "requestId": "req-..." }
}
```

Erros seguem:

```json
{
  "success": false,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Dados inválidos",
    "details": { "email": "Formato inválido" }
  },
  "meta": { "timestamp": "...", "requestId": "req-..." }
}
```

| Código | HTTP | Ocorrência (exemplos) |
|--------|------|-----------------------|
| `VALIDATION_ERROR` / `BAD_REQUEST` | 400 | Falha em DTOs Zod (`RegisterDTO`, `DepositDTO`, etc.). |
| `UNAUTHORIZED` | 401 | Token ausente/expirado. |
| `NOT_FOUND` | 404 | Usuário, carteira ou aposta inexistente. |
| `CONFLICT` | 409 | Email duplicado, mudança de email inválida, carteira já criada. |
| `RATE_LIMIT_EXCEEDED` | 429 | Limite global ou específico atingido. |
| `INTERNAL_SERVER_ERROR` | 500 | Erro inesperado não tratado. |

## Rate limiting

- **Global:** `express-rate-limit` (defaults `windowMs=600000`, `max=5000`). Configure com `RATE_LIMIT_{WINDOW_MS,MAX,MESSAGE,ENABLED}`.
- **Por rota:** `createRouteRateLimiter` injeta limites para endpoints críticos.

| Rota | Variáveis | Padrão |
|------|-----------|--------|
| `POST /auth/register` | `AUTH_REGISTER_RATE_LIMIT_*` | `window=60s`, `max=10` |
| `POST /auth/login` | `AUTH_LOGIN_RATE_LIMIT_*` | `window=60s`, `max=15` |
| `POST /auth/refresh` | `AUTH_REFRESH_RATE_LIMIT_*` | `window=60s`, `max=30` |
| `POST /wallets/deposit` | `WALLET_DEPOSIT_RATE_LIMIT_*` | `window=60s`, `max=20` |
| `POST /wallets/withdraw` | `WALLET_WITHDRAW_RATE_LIMIT_*` | `window=60s`, `max=10` |
| `POST /bets` | `BET_PLACE_RATE_LIMIT_*` | `window=60s`, `max=30` |
| `POST /bets/:betId/cancel` | `BET_CANCEL_RATE_LIMIT_*` | `window=60s`, `max=10` |

Headers retornados (`RateLimit-Limit`, `RateLimit-Remaining`, `RateLimit-Reset`) seguem o padrão IETF.

### Contact (`/api/contact`)

Contato público para mensagens ao time de suporte/ops. O endpoint valida payload mínimo e enfileira a mensagem para processamento assíncrono por um worker (Bull + Redis) ou por um adaptador em memória em ambientes de teste.

| Método | Caminho | Notas |
|--------|---------|-------|
| `POST` | `/contact` | Aceita `{ name?, email?, message, recaptchaToken? }`. `message` é obrigatório (mínimo 3 caracteres). A requisição é validada via Zod e, em caso de sucesso, o payload é enfileirado para a fila `contact_queue` e um `ticketId` é retornado com HTTP `202 Accepted`. |

Comportamento importante:
- ReCAPTCHA: se `RECAPTCHA_SECRET` estiver configurada, o backend valida o token recebido em `recaptchaToken`. Rejeições retornam `400 BAD_REQUEST`.
- Anti-spam: heurísticas simples (palavras proibidas) podem bloquear a mensagem e gerar `400 BAD_REQUEST` com `Mensagem bloqueada por conteúdo`.
- Fila/worker: por padrão o projeto usa `InMemoryMailerQueue` em `test`/`dev`. Para produção, habilite `USE_REDIS_QUEUE=true` e rode o worker (veja Quickstart). O worker consome jobs `contact` e envia emails via `nodemailer`.

Exemplos (curl):

```bash
# Enviar uma mensagem de contato simples
curl -X POST http://localhost:3000/api/contact \
  -H 'Content-Type: application/json' \
  -d '{"name":"Jane","email":"jane@example.com","message":"Olá suporte"}'

# Enviar com token reCAPTCHA (quando habilitado)
curl -X POST http://localhost:3000/api/contact \
  -H 'Content-Type: application/json' \
  -d '{"name":"Jane","email":"jane@example.com","message":"Olá suporte","recaptchaToken":"TOKEN_AQUI"}'
```

### Usuários (`/api/users`)

Todas protegidas por bearer token + cache opcional (`cacheUserProfileMiddleware`).

| Método | Caminho | Notas |
|--------|---------|-------|
| `GET` | `/users/me` | Retorna perfil completo; servido do Redis quando `CACHE_ENABLED=true`. |
| `PATCH` | `/users/me` | Atualiza `firstName/lastName` (o backend recalcula `username` e `updatedAt`). |
| `PATCH` | `/users/me/email` | Troca email após validar unicidade e VO `Email`. Limpa cache de perfil. |
| `GET` | `/users/me/pix-key` | Retorna a chave Pix padrão vinculada ao usuário (vazio quando não configurada). |
| `PUT` | `/users/me/pix-key` | Aceita `{ pixKey }`, valida comprimento/formato e salva como fallback para saques e PIX automáticos. |

| `POST` | `/users/me/documents` | `protectedRoute` + multipart upload. Aceita campo `document` (imagem ou PDF, até 5MB). Armazena metadados do arquivo no perfil do usuário e devolve `{ document }` com `id, url, mimeType, size, uploadedAt`. No ambiente local os arquivos são servidos em `/uploads` (LocalStorageAdapter); em produção recomendamos usar object storage (S3/GCS) e URLs assinadas. |

Exemplo (curl multipart):

```bash
# upload de documento (requere Authorization: Bearer <userId|token>)
curl -X POST http://localhost:3000/api/users/me/documents \
  -H "Authorization: Bearer dev-user-123" \
  -F "document=@/path/to/id.jpg" \
  -v
```

### Carteiras (`/api/wallets`)

| Método | Caminho | Proteções / Cache | Descrição |
|--------|---------|-------------------|-----------|
| `GET` | `/wallets/me` | `protectedRoute` + `cacheWalletBalanceMiddleware` | Carteira atual `{ userId, balance, lockedBalance, currency }`. |
| `GET` | `/wallets/history?limit&offset` | `protectedRoute` + `cacheWalletHistoryMiddleware` | Histórico paginado (`transactions`, `pagination`). |
| `POST` | `/wallets/deposit` | `protectedRoute` + rate limit `wallet-deposit` | Body `{ amount, currency, description? }` (mínimo configurável via `WALLET_MIN_DEPOSIT`, default **R$ 1,00**). Responde 201 com `{ wallet, pix }`, onde `pix` traz `chargeId`, `reference`, `provider`, `status`, `qrCode`, `expiresAt`, `confirmedAt`. |
| `POST` | `/wallets/withdraw` | `protectedRoute` + rate limit `wallet-withdraw` | Body `{ amount, currency, pixKey?, description? }`. Quando `pixKey` não é enviado usamos a chave padrão do usuário (configure em `/users/me/pix-key`). Mínimo ajustável via `WALLET_MIN_WITHDRAW` (default **R$ 100,00**). Retorna `{ wallet, pix }` com `payoutId`, `reference`, `provider`, `status`, `processedAt`. |

> **Mock Pix provider:** os fluxos de depósito e saque usam o `PixProviderPort`, que no ambiente atual aponta para `MockPixProvider`. Ele gera QR Codes determinísticos e confirma o pagamento imediatamente, expondo todos os metadados no response (`pix.*`) e no histórico (`transactions[].metadata`). Nenhum valor sai do ambiente — é apenas uma simulação confiável para QA/integrações.

> **Limites monetários:** `appConfig.wallet.limits` lê `WALLET_MIN_DEPOSIT` (default R$ 1,00) e `WALLET_MIN_WITHDRAW` (default R$ 100,00). Qualquer valor abaixo retorna `400 VALIDATION_ERROR`. Garanta que o front valide antes de enviar e mostre a mensagem "valor abaixo do mínimo" quando necessário.

> **Toggles Pix:** use `PIX_ENABLE_DEPOSITS` / `PIX_ENABLE_WITHDRAWALS` para suspender fluxos rapidamente sem desligar o restante do backend. Quando `false`, o controller devolve `503 SERVICE_UNAVAILABLE` antes de chamar os use cases.

#### Pix simulado (determinístico)

- Provider atual: `MockPixProvider` (`PIX_PROVIDER=mock`), configurável via `PIX_PROVIDER_NAME`, `PIX_MOCK_LATENCY_MS` e `PIX_DEFAULT_KEY` (chave fallback exibida para usuários).
- Depósitos expõem um QR Code fake pronto para copiar/colar e o backend já confirma o pagamento (`status: PAID`) para acelerar o fluxo de testes.
- Saques exigem `pixKey` no payload e respondem com `pix.payoutId/reference` para rastreabilidade — as mesmas informações são persistidas em `transactions[].metadata` e replicadas na treasury para auditorias futuras.
- Em produção, basta implementar outro adapter (`PixProviderPort`) e alterar `PIX_PROVIDER` para usar o gateway real, sem tocar nos controllers ou serviços.

> **Política de encerramento:** antes de excluir uma conta de usuário, processe um saque integral aprovado para zerar o saldo. Se não houver dados suficientes para saque, transfira o valor remanescente para a carteira da casa (treasury) e registre o motivo para auditoria.

### Finanças (`/api/finance`)

| Método | Caminho | Descrição |
|--------|---------|-----------|
| `GET` | `/finance/packages` | Lista pacotes ativos (`CreditPackageResponseDTO`). |
| `POST` | `/finance/packages/:packageId/purchase` | Compra pacote, credita `base+bonus` e retorna `{ wallet, creditPackage }`. |
| `POST` | `/finance/withdrawal-requests` | Cria solicitação `{ amount, currency, notes? }`, trava o saldo (`wallet.lock`) e coleta os dados de PIX/documentos/notas fiscais — se o usuário estava `PENDING_VERIFICATION`, ele é promovido para `ACTIVE` nesse momento. |
| `GET` | `/finance/withdrawal-requests` | Lista pedidos do usuário com `approvalLogs`. |
| `PATCH` | `/finance/withdrawal-requests/:requestId` | Admin flow: `{ action: "APPROVED"&#124;"REJECTED", notes? }`. Atualiza `withdrawLocked`/`unlock`. |

> **Tesouraria automática:** a faixa de destinação é dada pelos envs `TREASURY_MIN_PRIZE_RATIO` e `TREASURY_MAX_PRIZE_RATIO` (defaults 0.4–0.8). O alvo (`TREASURY_TARGET_PRIZE_RATIO`) é automaticamente "clampado" dentro dessa faixa sempre que chamamos `/api/admin/treasury/rebalance`, garantindo que o serviço nunca envie razões inválidas para o domínio.

### Jogos (`/api/games`)

> Backend de mini games. O primeiro jogo ativo é **Cara ou Coroa**, com payout fixo configurável. Os endpoints expõem integrações tanto para o front gráfico quanto para futuros adaptadores externos (webhook).

| Método | Caminho | Auth | Descrição |
|--------|---------|------|-----------|
| `GET` | `/games` | público | Lista jogos disponíveis (+ min/max bet, status). |
| `GET` | `/games/coin-flip` | público | Configuração atual do coin flip (habilitado, limites, payout fixo/multiplicador). |
| `GET` | `/games/coin-flip/feed` | público | Últimas 20 rodadas para exibir em dashboards/frontend. |
| `GET` | `/games/coin-flip/history?limit=` | bearer | Histórico pessoal (limite até 50). |
| `POST` | `/games/coin-flip/play` | bearer | Executa rodada; o backend debita a carteira, roda o mecanismo e paga o ganho fixo/multiplicador (ou retorna 503 se o jogo estiver desabilitado). |

#### Mecanismo e integrações

- O serviço `CoinFlipGameService` aplica validações de aposta (`minBet`/`maxBet`) e utiliza `WalletService` para debitar/creditar.
- `CoinFlipEngine` é um port determinístico (`GameEnginePort`).
- `GameIntegrationPort` permite conectar webhooks/WebSocket no futuro. Atualmente o factory cria um `NoopGameIntegrationAdapter` ou um webhook simples (`GAME_INTEGRATION_WEBHOOK_ENABLED=true` + `GAME_INTEGRATION_WEBHOOK_URL=https://...`).
- Configurações do jogo ficam em `appConfig.games.coinFlip` (vide seção de Config).

## Ferramentas e exemplos

### Swagger / Postman

- Acesse `/api/docs` e clique em **Authorize** para informar o bearer token (`accessToken` recebido em `/auth/login`).
- Para Postman/Insomnia, importe `/api/docs.json`, defina `&#123;&#123;baseUrl&#125;&#125;` e injete `&#123;&#123;accessToken&#125;&#125;` no header `Authorization`.

### cURL de referência

## Configurações relevantes

- **Cache:** `CACHE_ENABLED`, `REDIS_URL`, `CACHE_USER_BALANCE_TTL_SECONDS`, `CACHE_WALLET_HISTORY_TTL_SECONDS`, `CACHE_ODDS_TTL_SECONDS`.
- **Persistência Mongo:** `USE_MONGOOSE_PERSISTENCE`, `MONGO_URL` (afetando `/readiness` e os repositórios). 
- **Tracing:** `TRACING_ENABLED`, `OTEL_EXPORTER_OTLP_ENDPOINT`, `OTEL_SERVICE_NAME`, `OTEL_DIAGNOSTIC_LOG_LEVEL`.
- **Rate limiting:** `RATE_LIMIT_*`, `AUTH_*_RATE_LIMIT_*`, `WALLET_*_RATE_LIMIT_*`, `BET_*_RATE_LIMIT_*`.
- **Admin:** `ADMIN_USER_IDS` (CSV de IDs internos que podem usar `/api/admin/**`).
- **Games:** `GAME_COINFLIP_ENABLED`, `GAME_COINFLIP_MIN_BET`, `GAME_COINFLIP_MAX_BET`, `GAME_COINFLIP_PAYOUT_MULTIPLIER`, `GAME_COINFLIP_FIXED_WIN`, `GAME_INTEGRATION_WEBHOOK_ENABLED`, `GAME_INTEGRATION_WEBHOOK_URL`.

Proteja `/health`, `/readiness` e `/health/cache` via firewall ou reverse proxy em produção caso necessário (o `/metrics` responde 410 enquanto `OBS_ENABLE_PROMETHEUS=false`).
