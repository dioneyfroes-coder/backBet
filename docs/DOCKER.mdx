# Docker — Fase 17

## Visão geral

Este projeto assume o ambiente real:

```text
PC de desenvolvimento
   │  (Windows — escreve código, roda testes, valida build)
   ▼
host Docker (Linux/Ubuntu + Docker)
   ├── backbet (API)                  porta 3000 (BACKBET_PORT)
   ├── withdrawal-worker
   ├── contact-worker
   ├── redis:7 (cache + filas Bull)   rede interna (sem porta pública)
   └── mongodb:7 (replica set rs0)    rede interna (sem porta pública)
        └── mongo-rs-init (one-shot: rs.initiate())
```

**Tudo roda em Docker no mesmo host**, orquestrado por um único
`docker-compose.yml`. O MongoDB e o Redis são serviços internos da rede do
Compose e **não publicam porta pública**; a API é o único ponto exposto (via
porta `BACKBET_PORT` ou pelo reverse proxy — `docs/DEPLOY.mdx`).

> Requisito técnico: o app usa transações MongoDB (wallet, ledger, bet,
> treasury). Transações exigem **replica set** — por isso o serviço `mongodb`
> roda um replica set de nó único (`rs0`) e o `mongo-rs-init` executa o
> `rs.initiate()` automaticamente na primeira subida.

## Arquivos desta fase

| Arquivo | Função |
|---|---|
| `Dockerfile` | build multi-stage (builder + runtime produção) |
| `.dockerignore` | mantém o contexto pequeno e sem segredos |
| `docker-compose.yml` | **host único**: MongoDB + `mongo-rs-init` + Redis + API + workers |
| `docker-compose.observability.yml` | overlay (opcional): Prometheus + Grafana + OpenTelemetry Collector |
| `docker-compose.proxy.yml` | overlay (opcional): Caddy (TLS) como ponto público |
| `deploy/mongo/init-app-user.sh` | cria os usuários (app + teste) no boot do Mongo |
| `deploy/observability/*` | configs de Prometheus, OTel e Grafana (opcional) |
| `.env.example` | modelo seguro de variáveis |

## Pré-requisitos

- Docker Engine + Compose v2 no host (Ubuntu:
  `sudo apt install docker.io docker-compose-v2` e habilite o serviço).
- Porta `BACKBET_PORT` (default `3000`) livre para a API. Com o overlay de
  proxy, apenas `80/443` ficam públicos.

## Passo 1 — Variáveis de ambiente

```bash
cp .env.example .env
# edite o .env e preencha:
#   JWT_SECRET=...                    (gere com: openssl rand -hex 32)
#   MONGO_ROOT_PASSWORD=senha-forte   (usuário admin do Mongo)
#   MONGODB_APP_PASSWORD=senha-app    (usuário readWrite do backbet)
#   MONGODB_TEST_PASSWORD=senha-test  (usuário da suíte de integração)
#   MONGODB_URI=mongodb://backbet:senha-app@mongodb:27017/backbet?authSource=admin&replicaSet=rs0
#   REDIS_URL=redis://:senha@redis:6379
```

Os hostnames `mongodb` e `redis` são os nomes dos serviços na rede interna do
Compose — não precisam resolver no host.

## Passo 2 — Imagem da aplicação

A forma mais simples é **build no próprio host**:

```bash
docker compose build            # target: runtime (imagem backbet:latest)
```

Alternativa (build no PC de dev + transferência):

```bash
# no PC de desenvolvimento
docker build -t backbet:latest .
docker save backbet:latest | gzip > backbet.tar.gz
scp backbet.tar.gz user@<host>:/tmp/
# no host
docker load < /tmp/backbet.tar.gz
```

## Passo 3 — Subir tudo no host

```bash
docker compose up -d --build
```

O compose sobe, em ordem de dependência:

- `mongodb` — `mongo:7` em replica set `rs0`, com autenticação e healthcheck;
- `mongo-rs-init` — container one-shot que executa o `rs.initiate()` e só
  termina quando o nó vira `PRIMARY` (a app espera por ele);
- `redis` — cache + filas, **sem porta publicada** (acesso interno apenas);
- `backbet` — a API (porta `3000` publicada, `BACKBET_PORT` para trocar);
- `withdrawal-worker` — consome `withdrawal_payouts` (Bull/Redis), paga via
  adaptador Pix e atualiza o MongoDB;
- `contact-worker` — consome `contact_queue` e envia e-mails (SMTP ou
  `jsonTransport`).

Smoke test:

```bash
docker compose ps                       # todos healthy (mongo-rs-init concluído)
docker compose logs -f backbet          # logs: Mongo conectado, servidor up
curl -sf http://localhost:3000/health
curl -sf http://localhost:3000/readiness
curl -sf http://localhost:3000/api/docs.json > /dev/null && echo docs ok
docker compose logs -f withdrawal-worker
docker compose logs -f contact-worker
```

Operações administrativas (migrations/seeds) via containers:

```bash
docker compose exec backbet node dist/scripts/runMigrations.js
docker compose exec backbet node dist/scripts/seedHouseTreasury.js
```

## Operação comum

| Ação | Comando (no host) |
|---|---|
| Reconstruir e subir | `docker compose up -d --build` |
| Logs da API | `docker compose logs -f backbet` |
| Logs de um worker | `docker compose logs -f withdrawal-worker` |
| Parar (mantém volumes) | `docker compose down` |
| Deletar tudo (inclui dados) | `docker compose down -v` |
| Reiniciar um serviço | `docker compose restart backbet` |
| Subir só a API + Redis | `docker compose up -d redis backbet` |

Dados persistidos (todos no mesmo host, como volumes nomeados):
`mongodb_data`, `redis_data`, `backbet_logs`, `backbet_uploads`.

## IP do laboratório (decisão deliberada)

O `docker-compose.yml` publica as portas do MongoDB (`27018`) e do Redis
(`6379`) **apenas no IP `192.168.22.250`** — o IP estático do `server01`.

> Este IP é **deliberadamente estático** e **não deve ser interpretado como
> configuração acidental**. As portas publicadas nesse IP fazem parte da
> decisão consciente de laboratório (ex.: acesso humano aos dados via tools do
> Mongo/Redis a partir da rede local). Os serviços continuam internos à rede
> do Compose para a aplicação (`mongodb:27017` / `redis:6379`).

Para alterar o bind (ex.: outro host, ou nenhuma publicação), use `LAB_BIND_IP`
no `.env`:

```ini
# Default: 192.168.22.250 (lab)
LAB_BIND_IP=127.0.0.1        # publica só em loopback
LAB_BIND_IP=                 # não publica porta (serviço interno apenas)
```

No `docker-compose.yml`, o default fica codificado como
`${LAB_BIND_IP:-192.168.22.250}` — o composição real mantém o IP fixo do lab,
mas qualquer outro host pode sobrescrever sem editar o arquivo.

## Reconstrução limpa (Fase 17 — drill)

O drill de reconstrução limpa valida que todo o ambiente nasce de um estado
vazio. Roda de ponta a ponta o ciclo previsto no plano:

```text
docker compose down -v           (1) limpeza total
docker compose build --no-cache  (2) build sem cache
docker compose up -d             (3) subir tudo
docker compose ps                (4) estado dos containers
curl /health                     (5) API saudável
curl /readiness                  (5) Mongo + Redis prontos
```

Uso:

```bash
# no server01 (mantém a stack de pé ao final)
npm run docker:rebuild

# em CI / host sem o IP do lab (derruba a stack ao final)
LAB_BIND_IP=127.0.0.1 npm run docker:rebuild:ci

# com build em cache (mais rápido, para iteração local)
bash scripts/docker-rebuild-drill.sh --cache
```

O script valida:

- `mongodb`, `redis` e `backbet` **healthy** no `docker compose ps`;
- `withdrawal-worker` e `contact-worker` **Up** com log de inicialização;
- `GET /health` → `status: "healthy"`;
- `GET /readiness` → `ready: true` com `checks.mongo.status` e
  `checks.redis.status` = `up`.

O mesmo drill roda no workflow **Nightly** (job `docker-rebuild`, Fase 17),
agendado/manual, para detectar regressões de Dockerfile/Compose sem custo no
PR gate.

> ⚠️ `docker compose down -v` **apaga os volumes** (`mongodb_data`, `redis_data`,
> `backbet_logs`, `backbet_uploads`). O drill pede confirmação em ambientes
> interativos; use `--yes` apenas quando a perda de dados é aceitável (ex.: CI).

## Segurança (mínimo operacional)

- `JWT_SECRET` forte e fora do Git (`.env` é ignorado);
- Mongo autenticado, usuário da app com `readWrite` apenas no banco `backbet`;
- MongoDB e Redis **internos** ao Compose (sem porta pública);
- não use `ALLOW_DEV_BEARER_BYPASS=true` fora de laboratório;
- `OBS_ENABLE_PROMETHEUS=true` expõe `/metrics` — restrinja via firewall/proxy.

## Troubleshooting

| Sintoma | Causa provável / solução |
|---|---|
| `MongoNetworkError` na API | `MONGODB_URI` errada; serviço `mongodb` ainda subindo (`docker compose ps`) |
| Transações falham (`Transaction numbers are only allowed on a replica set`) | `mongo-rs-init` não concluiu — cheque `rs.initiate` (`myState: 1`) e `docker compose logs mongo-rs-init` |
| API sobe, mas `readiness` não passa no Mongo | Mongo ainda inicializando (`docker compose ps` / logs do `mongodb`) |
| Worker de saque não processa | `REDIS_URL`/filas: use `redis://redis:6379` e `USE_REDIS_QUEUE=true` (já padrão no compose); cheque `docker compose logs -f withdrawal-worker` |
| Porta 3000 ocupada | defina `BACKBET_PORT` no `.env` |
| E-mails não saem | sem `MAILER_SMTP_URL` o worker usa `jsonTransport` (grava somente) |
| `docker compose up` pede `.env` | `cp .env.example .env` e preencha `JWT_SECRET`, `MONGODB_URI` e `MONGODB_APP_PASSWORD` |
