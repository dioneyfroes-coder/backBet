# Usuários, Identidade e Autenticação

Este documento cobre o ciclo de vida do usuário no BackBet (módulo `src/core/user`) e a autenticação via Passport/JWT.

## Ciclo de vida do usuário

1. **Registro** — `POST /api/v1/auth/register` cria `User` + `Wallet` (BRL padrão). O usuário nasce `PENDING_VERIFICATION` ou `ACTIVE`, conforme a política de verificação configurada.
2. **Verificação (polling)** — usuários `PENDING_VERIFICATION` fazem polling em `GET /api/v1/auth/register/status/:userId` até `isActive=true`.
3. **Ativação** — quando ativo, o registro retorna `accessToken`/`refreshToken` + `sessionId`.
4. **Login** — `POST /api/v1/auth/login` (email/senha) devolve tokens.
5. **Perfil** — `GET/PUT /api/v1/users/me`, `GET /api/v1/users/me/preferences`, `POST /api/v1/users/me/documents` (upload multipart).
6. **Saída** — revogação de sessão quando aplicável.

## Autenticação

### Estratégias Passport

- **Produção**: `passport-jwt` valida o `Authorization: Bearer <JWT>` emitido pelo `JwtService` local (ou provedor de identidade via adapter). O token carrega `userId` e `sessionId`.
- **Dev/Test**: com `ALLOW_DEV_BEARER_BYPASS=true`, `Bearer <userId>` (valor sem formato JWT `AAA.BBB.CCC`) é tratado como userId diretamente — facilita testes locais sem provedor.
- **ID token (provedor de identidade)**: cadastro/atualização sincronizam o `providerId` quando configurado.

### JWT

- Assinatura: `JWT_SECRET` (**obrigatória sempre** — o boot lança erro sem ela). Custo de hash de senha: bcrypt **12**.
- Validade configurável; renovação via `/api/v1/auth/refresh` (quando habilitada) ou fluxo do provedor.
- Tokens expirados → `401 UNAUTHORIZED`; sem permissão → `403 FORBIDDEN`.

### Proteção de rotas

- `protectedRoute` exige token válido e preenche `req.auth.userId`.
- `requireAdminRole` restringe `/api/v1/admin/*` (papel `ADMIN`, configurado por `ADMIN_USER_IDS`).
- Middlewares de autenticação: `src/infrastructure/api/middleware/AuthMiddleware.ts`.

## Rate limits de autenticação

- Globais + específicos da rota: `AUTH_LOGIN_RATE_LIMIT_*`, `AUTH_REGISTER_RATE_LIMIT_*` (abusos de login/registro são contidos por `createRouteRateLimiter`).

## Upload de documentos

- `POST /api/v1/users/me/documents` (`multipart/form-data`) — usado para KYC quando o port de verificação estiver ativo.
- Os arquivos não são versionados; considere bucket privado em produção.

## Segurança

- Nenhum segredo/`password` em logs — o `requestContext` expõe apenas `userId`.
- Hash com custo 12 testado (bcrypt) — `Security.test.ts`.
- CORS por allowlist + helmet + payload limit `10mb`.

## Games (requisitos de auth)

O módulo de games compartilha a mesma autenticação:

- `GET /api/v1/games` e `GET /api/v1/games/coin-flip/feed` — **públicos**.
- `GET /api/v1/games/coin-flip/history` e `POST /api/v1/games/coin-flip/play` — **auth obrigatória** (mesma `Authorization`).
- No endpoint `play`, o backend debita a carteira (`WalletService`) **antes** de jogar; resposta inclui `outcome`, `result`, `payoutAmount` e `createdAt`. `503` = jogo desligado (`GAME_COINFLIP_ENABLED=false`).
- Detalhes completos (estados, `play-batch`, prêmio fixo): `docs/Bet_docs.mdx`.
