# Matriz de Cenários Críticos (Fase 20)

Matriz que cobre os cenários **críticos para o dinheiro** do MVP: Carteira,
Aposta, Settlement, Withdrawal e Pix. Cada cenário indica **onde** ele é
validado (arquivo:linha) ou se é uma **lacuna** — incluindo lacunas de
**funcionalidade** (não é só teste faltando, é código que não existe).

Legenda de status:

- **Coberto** — existe teste automático que valida o cenário.
- **Novo (Fase 20)** — teste adicionado nesta fase.
- **Parcial** — o caminho principal está coberto, mas um detalhe não.
- **Funcionalidade não existe** — não há teste possível sem antes implementar a
  funcionalidade (registrado como dívida/risco, ver seção Pix).

> **Por que os cenários P1-P7 estão marcados como "funcionalidade não existe":**
> o código atual **não implementa recebimento de webhook Pix**. O pagamento é
> confirmado de forma **síncrona** no depósito via `MockPixProvider`
> (`payWithdrawal`/`confirmPayment`), e o saque assume `COMPLETED` imediatamente
> quando o port de pagamento responde sucesso. O único webhook recebido pelo
> sistema é o de jogo (outgoing gate, `WebhookGameIntegrationAdapter.ts`).
> Os 7 cenários de webhook Pix do plano **não podem ser testados** até que a
> funcionalidade seja construída (rota `POST /api/webhooks/pix`, identificação
> da charge por reference, validação de valor/status e idempotência por evento
> externo). Isso é **dívida/risco registrado da Fase 20** e deve entrar no
> backlog da integração Pix real (mock PSP síncrono atual não cobre).

## Lacunas registradas que exigem decisão

1. **Webhook Pix** (P1-P7) — precisa de funcionalidade nova antes de qualquer
   teste. Recomendado: implementar rota de webhook com idempotência por
   `chargeId`, validação de `reference`/`amount`/`status` e guarda contra
   duplicidade, seguida dos 7 testes acima.
2. **Rollback real com transação Mongo** (W1/B8) — a simulação in-memory prova a
   orquestração do `BetService` (saldo restaurado, sem aposta, sem movimento de
   ledger), mas o rollback efetivo com `withTransaction` do MongoDB exige a
   suíte de integração contra o replica set (`npm run test:integration:full`)
   — adicionar caso lá é o próximo passo natural.
3. **Limite de exposição na aposta via HTTP** — a rejeição por `RISK_LIMIT_EXCEEDED`
   tem cobertura unitária; um teste HTTP com risco estourado fecharia o ciclo
   admin → aposta.
