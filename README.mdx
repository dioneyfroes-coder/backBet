# BackBet – Visão Geral

BackBet é um backend de apostas desportivas construído em **TypeScript/Node 22+**, seguindo **DDD**, camadas limpas e observabilidade nativa. Todos os módulos vivem em `src/` e são expostos via Express 5, com autenticação baseada em JWT (ou provedores de identidade configuráveis), cache Redis, persistência Mongo opcional e métricas/tracing configuráveis.

## Stack e princípios

- **Linguagem/Runtime**: TypeScript 5.9 + Node 22+ (`ts-node`/`tsx` em dev, `tsc` + `tsc-alias` para build)
- **Nomes configuráveis**: `APP_NAME` declara o nome do produto exibido enquanto `SERVICE_NAME` identifica o serviço em métricas/tracing (`OTEL_SERVICE_NAME`). Mantemos ambos no `.env` para separar a identidade do app da identidade operacional.
- **Configuração centralizada**: `BACKBET_RUNTIME_ENV` decide se as validações de produção devem exigir chaves live; mantenha em `development` para tolerar valores de `.env` mesmo quando ferramentas (PM2 e scripts de observabilidade) precisam que `NODE_ENV=production`.
- **Arquitetura**: Monólito modular (API ▸ application ▸ domain ▸ infrastructure ▸ shared)
- **Padrões**: DDD, Result pattern, repositories async, factories para troca de adapters
- **Qualidade**: ESLint flat config, Jest + ts-jest, testes unitários e de integração, CI local `npm run lint && npm run test -- --coverage && npm run build`
- **Observabilidade**: health/readiness endpoints, snapshots internos de cache/resiliência, request-id + logs JSON, OpenTelemetry e PM2 WebUI (em rollout)

## Bounded contexts

| Contexto | Diretório | Responsabilidades | Principais artefatos |
|----------|-----------|-------------------|----------------------|
| **User Core** | `src/core/user` | Registro, autenticação local e sincronização com provedores de identidade externos, atualização de perfil/email. | `User`, `Email`, `RegisterUser`, `AuthController`, `UserController` |
| **Finance Core** | `src/core/finance` | Carteiras, depósitos/saques, pacotes de crédito, workflow de withdrawal locks. | `Wallet`, `Money`, `WalletService`, `WithdrawalRequestService` |
| **Betting Core** | `src/core/betting` | Eventos, odds, colocação/cancelamento/resolução de apostas. | `Bet`, `Event`, `PlaceBet`, `BetController` |
| **Shared Kernel** | `src/core/shared` | `AggregateRoot`, `UniqueId`, `Result`, `DomainError`, DTOs paginados, tipos comuns. | - |

Interfaces (`IUserRepository`, `IWalletRepository`, `IBetRepository`, etc.) isolam o domínio; factories em `src/infrastructure/persistence/factory.ts` escolhem entre adaptadores in-memory e Mongo/Mongoose.

## Fluxo ponta a ponta

1. Request chega ao `ApiServer` → middlewares aplicam helmet, CORS, rate limit, request-id, logging e métricas.
2. Autenticação via provedores de identidade externos (produção) ou bypass/JWT (`JwtService`) em dev/test; rotas sensíveis reutilizam `protectedRoute` + guards adicionais.
3. Controllers (auth, users, wallets, finance, bets) validam DTOs Zod e delegam para use cases (`src/core/**/application/use-cases`).
4. Use cases conversam com serviços de domínio (`UserService`, `WalletService`, `BetService`) e repositórios resolvidos via factory.
5. Cache Redis e hooks (`cacheUserProfile`, `cacheWalletBalance`, `cacheEventOdds`, etc.) reduzem IO e são invalidados após mutações.
6. Respostas seguem envelope padrão `{ success, data|error, meta: { requestId, timestamp } }`, garantindo rastreabilidade com logs/traces.

## Camadas principais

- **API (`src/infrastructure/api`)**: `ApiServer`, controllers, DTOs, middlewares (`loggingMiddleware`, `requestIdMiddleware`), Swagger (`/api/docs`).
- **Application**: Use cases por contexto (`RegisterUser`, `DepositFunds`, `PlaceBet`, `ChangeEmail`, etc.), com Result pattern.
- **Domínio**: Entidades/VOs puros (`User`, `Wallet`, `Bet`, `Money`, `Email`, `Odds`), regras e invariantes.
- **Infraestrutura**: Persistência (Mongo/in-memory), cache Redis, auth (provedores externos / JWT), observabilidade (metrics/tracing), config loaders.
- **Shared**: `AppError`, `requestContext`, configs centralizadas (`appConfig`, `cacheConfig`, `observabilityConfig`).

## Infraestrutura e dependências

| Componente | Estado | Detalhes |
|------------|--------|----------|
| **MongoDB / Mongoose** | Opcional em dev, recomendado em staging/prod | Ativado com `USE_MONGOOSE_PERSISTENCE=true`; schemas em `src/infrastructure/persistence/mongoose/schemas`. `connectMongoDB()` é chamado antes do `ApiServer`. |
| **Redis** | Opcional em dev, recomendado em produção | Config em `shared/config/cacheConfig.ts`. `RedisClient` expõe métricas e flush helpers para manter consistência. |
| **Identidade externa** | Obrigatório em produção | Middleware do provedor de identidade configurado. Dev/test podem usar bypass definindo `ALLOW_DEV_BEARER_BYPASS=true` ou `JwtService` local. |
| **JWT local** | Usado nos endpoints `/auth/login` & `/auth/refresh` | `JwtService` gera/valida tokens; útil para testes E2E sem provedor de identidade. |
| **Observabilidade** | Default ON | `/health`, `/health/cache`, `/readiness` e tracing (`TRACING_ENABLED`) com exportador OTLP configurável; por padrão `/metrics` responde `410` até que `OBS_ENABLE_PROMETHEUS=true`. PM2 WebUI + health monitor cobrem o restante da stack. |

## APIs e contratos

- Swagger UI em `/api/docs` + JSON em `/api/docs.json` (`docs/openapi.json`).
- Documentação textual em `docs/API_DOCS.mdx` e `docs/OBSERVABILITY.mdx`.
- Controllers seguem `BaseController` e `asyncHandler`, retornando envelopes padronizados e códigos `AppError` (ex.: `RATE_LIMIT_EXCEEDED`, `VALIDATION_ERROR`).
- Rate limits globais (`appConfig.rateLimit`) e específicos (`AUTH_*_RATE_LIMIT_*`, `WALLET_*_RATE_LIMIT_*`, `BET_*_RATE_LIMIT_*`).
- Operações mutáveis aceitam `Idempotency-Key`, reservado com Redis `SET NX` quando habilitado.
- `Money` e `BetAmount` fazem aritmética interna em centavos inteiros, mantendo números na API.
- `HouseWallet` usa optimistic locking por `version` e retorna `409 CONFLICT` em versão obsoleta.

## Execução local

1. `cp .env.example .env`
2. Ajustar variáveis: `NODE_ENV=development`, `CACHE_ENABLED=false` (caso sem Redis), `USE_MONGOOSE_PERSISTENCE=false` (para in-memory) ou definir `MONGODB_URI`.
3. `npm install`
4. `npm run dev` (hot reload com `tsx`)
5. Exercitar rotas (`curl`, Postman, Swagger) e acompanhar health/readiness e logs estruturados (métricas estão sendo migradas para PM2 WebUI).

### Pipelines úteis

- `npm run lint`
- `npm run test --coverage`
- `npm run build`
- `RUN_REAL_INTEGRATION_TESTS=true npm test -- --runInBand src/integration/__tests__/mongo-redis.integration.test.ts` (MongoDB + Redis reais)
- `npm start` (executa `dist/index.js`)

### Monitoramento diário

- Suba o painel com `npm run pm2:webui:start` (usa `PM2_WEB_PORT`, `PM2_WEB_USERNAME`, `PM2_WEB_PASSWORD` e respeita `OBS_USE_PM2_WEBUI`).
- Verifique CPU, memória e restarts do processo `backbet` direto no PM2 WebUI e complemente com `npm run pm2:webui:logs`.
- Continue usando `/health`, `/health/cache` e `/readiness` para probes externos; o antigo Grafana foi aposentado (ligue `OBS_ENABLE_PROMETHEUS=true` apenas para compatibilidade temporária com Prometheus).
- Inicie o monitor de saúde com `npm run pm2:health:start` (usa `HEALTH_MONITOR_*` + `SMTP_*` e só envia e-mails quando `OBS_ENABLE_EMAIL_ALERTS=true`); consulte `npm run pm2:health:logs` para acompanhar envios.
- Quando tudo estiver estável, finalize `pm2:webui:stop` e `pm2:health:stop` ou utilize `pm2 monit`/execuções pontuais (`HEALTH_MONITOR_RUN_ONCE=true npm run health-monitor:start`) em ambientes sem túnel seguro.

### Processos e PM2

- `npm run pm2:start` (build + `pm2 start ecosystem.config.cjs --env production`)
- `npm run pm2:reload`/`npm run pm2:stop`/`npm run pm2:logs` para controlar o cluster em produção
- Consulte `docs/PM2.mdx` para operações de zero downtime e monitoramento de métricas/health no cluster PM2.

### Feature toggles de observabilidade

- `OBS_USE_PM2_WEBUI` → controla se os scripts `pm2:webui:*` devem efetivamente subir o painel.
- `OBS_ENABLE_PROMETHEUS` → reativa `/metrics` com `prom-client`; deixe `false` para manter o retorno `410 Gone`.
- `OBS_ENABLE_EMAIL_ALERTS` → habilita/desliga o envio SMTP do `health-monitor` (o loop continua registrando falhas nos logs).

Cada mudança nesses toggles gera o log `observability_toggle_state` e o snapshot atual também aparece no campo `observability` das respostas `/health` e `/readiness`, facilitando auditoria sem depender do `.env`.

## Qualidade e operação

- Testes Jest (unidade + integração leve), executáveis com `npm run test -- --coverage`.
- A suíte MongoDB + Redis é opt-in e exige `RUN_REAL_INTEGRATION_TESTS=true`, `MONGODB_URI` e `REDIS_URL` de teste.
- Logs estruturados JSON com `request_start`, `request_end` e `request_error` (incluem requestId, userId, duração).
- Snapshots de saúde trackeiam dependências externas (Mongo, Redis e provedores de identidade configurados) e alimentarão a PM2 WebUI/alertas de saúde.
- Dashboards/alertas anteriores baseados em Prometheus/Grafana foram aposentados; o plano de migração está documentado em `docs/PM2-WEBUI-MIGRATION.mdx`.

## Novidades recentes

- `POST /api/contact`: novo endpoint público para contato. Mensagens são enfileiradas e processadas assincronamente por um worker (Bull+Redis em produção, adaptador em memória em dev/test).
- Worker de contato: `src/infrastructure/mailer/ContactWorker.ts` e script `src/scripts/start-contact-worker.ts`. Em dev rode `npm run worker:contact` ou use `ecosystem.contact.dev.config.cjs` com PM2.
- Upload de documentos: `POST /api/users/me/documents` (multipart, imagem/PDF, max 5MB). LocalStorageAdapter serve arquivos em `/uploads` para desenvolvimento.

## Boas Práticas e Checklist de Manutenção

> Siga este checklist para manter o projeto BackBet robusto, seguro e alinhado com as melhores práticas:

### 📦 Estrutura & Organização
- Novos módulos devem seguir o padrão `src/core/<domínio>/application/use-cases`.
- Revise periodicamente a pasta `docs/` para evitar documentação legada ou fora do padrão.
- Mantenha DTOs, controllers e rotas coesos em `src/infrastructure/api/**`.

### 🔒 Segurança
- Todas as rotas sensíveis devem usar autenticação e rate limiters.
- Nunca logue dados sensíveis (tokens, senhas, documentos completos).
- Audite CSP e headers de segurança ao adicionar novas UIs.
- Rode revisões de secrets e dependências (`npm audit`, `.env` no `.gitignore`).

### 🧪 Testes & Qualidade
- Mantenha cobertura de testes acima de 97% (statements/functions/lines).
- Priorize aumentar cobertura de branches (<90%) em módulos críticos (finance/bets).
- Adicione testes de carga (k6/Artillery) para `/auth`, `/wallets`, `/bets`.
- Automatize smoke tests pós-deploy (`/health`, `/readiness`, `/health/cache`).

### 🛠️ CI/CD & Dependências
- Automatize lint, test, build e audit no pipeline (GitHub Actions).
- Rode `npm outdated` a cada release e atualize libs críticas.
- Valide se pacotes dev-only não estão no runtime.

### 📄 Documentação & Observabilidade
- Atualize sempre os docs (`docs/*.mdx`) junto com mudanças de código.
- Documente exemplos de payloads e variáveis de ambiente.
- Adicione logs estruturados e snapshots em fluxos críticos.
- Enriquecer logs com métricas de produto (apostas, depósitos).

### 🏗️ Arquitetura & Roadmap
- Formalize eventos de domínio/outbox (`UserCreated`, `BetPlaced`, etc).
- Remova fallback in-memory em produção, habilite migrações automáticas.
- Prepare o `ApiServer` para escala horizontal e externalize sessões.
- Complete integração do PM2 WebUI + alertas de saúde.

### 🧹 Código & Imports
- Mantenha imports organizados e evite duplicidade.
- Use Zod para validação de DTOs em todos os controllers.
- Prefira objetos rasos nos logs e mensagens/eventos em inglês curto.

### 📝 Recomendações Gerais
- Exija descrição de testes executados nos PRs.
- Nunca logue tokens; revise PRs que toquem logging.
- Atualize docs no mesmo PR da mudança.
- Documente fallback e feature flags para integrações externas.
